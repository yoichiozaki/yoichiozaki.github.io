## Introduction: LLM Correctness Cannot Be Measured from One Output

LLM-backed chatbots are rapidly becoming the user-facing layer of many products: customer support, internal knowledge search, writing assistants, developer agents, and voice assistants. In these settings, users are not interacting with a model in isolation. They are interacting with <strong>a conversation system that includes model outputs</strong>.

How should we evaluate response quality? Traditional software tests assume that the same input produces the same output. LLM systems do not always behave that way. Even when the model, parameters, system prompt, user prompt, retrieved context, and tool definitions are fixed, the generated output may vary.

One run may answer in a careful bullet list. Another may say the same thing more briefly. A third may omit part of the evidence. In worse cases, a number, entity, condition, or final conclusion changes.

This article uses the following definitions.

> <strong>Output variance</strong>: differences in generated results that occur even when generation conditions are held fixed.
>
> <strong>Drift</strong>: differences in generated results caused by changes in generation conditions.

Here, variance means qualitative output variability, not only the statistical variance of a scalar metric.

Generation conditions include the model, model version, inference parameters, system prompt, user prompt, tool definitions, retrieval-index snapshot, reference documents, runtime policies, and backend system fingerprint. If the model was updated, the retrieval result changed, or the prompt was rewritten, the resulting difference is drift rather than variance in the sense used here.

In practice, the distinction is not always clean. If a provider updates a model behind an API, an observed difference may look like variance while actually being hidden drift. Evaluation logs should therefore record as much as possible: model ID, version or fingerprint, inference parameters, seed, prompts, retrieval results, tool outputs, system fingerprint, session state, memory, user profile, clock/timezone, cache state, side-effect state, and runtime identifiers.

When seed control is available, split evaluation into two modes.

| Mode | What is fixed | What it measures |
|---|---|---|
| <strong>Variance sampling</strong> | Model, prompts, retrieval/tool state, inference parameters, observed model revision / system fingerprint. Seed is unset or independently logged | The stochastic output distribution under fixed conditions |
| <strong>Determinism replay</strong> | All of the above plus seed and system fingerprint | Whether the run is mostly reproducible. Differences suggest hidden nondeterminism or drift |

Repeated calls with the same seed are closer to a reproducibility test than to sampling the model's stochastic output distribution. Mixing these modes makes variance numbers hard to interpret.

Even for variance sampling, runs with different observed fingerprints should not be mixed into the same population. Treat fingerprint changes as hidden drift or analyze them as separate strata.

The central claim of this article is simple.

<strong>The acceptability of an LLM response is not determined by one similarity score. It is determined by the combination of several kinds of variance: contract, surface, lexical, structural, information-selection, semantic, and pragmatic.</strong>

Exact match alone rejects harmless paraphrases. Embedding similarity alone can miss number changes or negation flips. LLM-as-judge alone imports the judge model's own variance into the evaluation process.

We need to stop saying that two outputs are merely “different” and instead measure what kind of difference occurred.

## 1. Shift the Unit of Evaluation from One Output to an Output Distribution

Let $c$ be the generation condition and $p$ be a prompt or evaluation case. If we run the same $p$ under the same $c$ for $n$ trials, the generated outputs are:

$$
Y_{p,c} = \{ y_1, y_2, \ldots, y_n \}
$$

Traditional tests often compare a single output $y$ with a ground truth $g$. To evaluate variance, however, the object of evaluation is not one $y$ but <strong>the output distribution under fixed conditions</strong>.

There are at least two comparisons to make.

| Comparison | Question | Examples |
|---|---|---|
| <strong>Against ground truth</strong> | How far is each output from the expected answer? | Reference text, expected JSON, rubric-based answer |
| <strong>Between outputs</strong> | How dispersed are outputs under the same condition? | Pairwise comparison, cluster count, pass/fail dispersion |

Ground-truth comparison alone cannot tell whether one good output was lucky or stable. Output-to-output comparison alone can miss the case where the system is consistently wrong. A variance evaluation therefore needs both <strong>distance from the answer</strong> and <strong>dispersion within the same condition</strong>.

A minimal protocol looks like this.

1. Fix the evaluation case $p$ and generation condition $c$.
2. Run the same case $n$ times. In practice, $n=5$ to $30$ is a reasonable screening range depending on cost.
3. Store all outputs. Keep not only final text but also tool calls, retrieval results, refusal reasons, token usage, and latency.
4. Compare each output with ground truth.
5. Compare outputs against each other.
6. Report not only averages but also worst cases, quantiles, pass rates, and cluster counts.

$n=5$ to $30$ is an exploratory range for finding dangerous variance early, not a precise reliability estimate. Always report pass rates with the denominator, such as `pass_count / n`, and preferably include uncertainty for the binomial proportion using a Wilson or Jeffreys interval. These intervals rely on the approximation that trials are effectively independent Bernoulli draws after a fixed binary gate. Real LLM calls may be correlated by caching, shared backend state, rate-limit batching, or judge reuse.

For release decisions, predeclare a criterion such as “the lower confidence bound must exceed 0.95” or “the upper bound on failure rate must be below 1%.” Even 30/30 successes do not prove rare-event safety; under an independent Bernoulli approximation, the one-sided 95% upper bound on failure probability after 30 zero-failure trials is still roughly 10%. For high-risk semantic and safety gates, do not overread 9/10 or 29/30 as stable; use larger samples and targeted boundary cases.

As a concrete anchor, if you observe zero failures and want the one-sided 95% upper bound on failure probability below 1% under independent trials, you need $n \ge \log(0.05) / \log(0.99)$, or about 299 zero-failure trials. This is only a rough illustration of how weak small samples are for proving production safety; real evaluations also need slice-level risk and trial-correlation analysis.

The goal is not to treat all variance as bad. Natural language has many correct realizations. For explanatory text, diversity may even be desirable. But in medical advice, contract terms, estimates, permissions, or operational procedures, a small variance can be a serious risk. The tolerance for variance depends on the task.

## 2. A Taxonomy of Variance: What Changed?

Output variance is not one phenomenon. A character may change, word choice may change, order may change, information may be omitted, meaning may change, or the conversational act may change. These differences have very different quality implications.

This article separates variance into seven layers.

| Layer | Kind of variance | What changes | Typical examples | Main measurements |
|---|---|---|---|---|
| 0 | <strong>Contract variance</strong> | Existence, format, constraints | Empty response, invalid JSON, wrong language, length violation | Schema validation, regex, language detection, length |
| 1 | <strong>Surface variance</strong> | Characters and notation | Punctuation, whitespace, casing, spelling variants | Exact match, normalized exact match, edit distance |
| 2 | <strong>Lexical variance</strong> | Words and phrases | “buy” vs “purchase”, “remove” vs “delete” | Token F1, n-grams, BLEU, chrF |
| 3 | <strong>Structural variance</strong> | Order, paragraphs, rhetorical organization | Reordered bullet points, conclusion first vs last | ROUGE-L, LCS, dependency/outline comparison |
| 4 | <strong>Information-selection variance</strong> | Included facts, evidence, level of detail | Omitted caveat, added example, missing source | Slot/claim extraction, coverage, precision/recall |
| 5 | <strong>Semantic variance</strong> | Propositions, relations, truth conditions | Number mismatch, negation flip, cause/effect reversal | Embedding similarity, NLI, QA checks, LLM judge |
| 6 | <strong>Pragmatic variance</strong> | Speech act, stance, risk posture | Refusal vs answer, different next action, confidence shift | Rubrics, human evaluation, LLM-as-judge, policy classifiers |

One output pair can differ at several layers at once. A large paraphrase changes characters, words, and structure. An incorrect number may have a tiny surface difference but a large semantic impact.

The object we try to make close to MECE is therefore not “one label per response pair.” It is <strong>the aspect being observed</strong>. The layers are diagnostic dimensions that separate what is primarily being observed, while real failures can span multiple layers. A missing required claim is information-selection variance and, depending on the task, semantic incompleteness. An unsafe recommendation can be observed as pragmatic variance but should still be rejected by an independent safety gate. The final decision should combine layer scores as a vector rather than forcing one label.

This taxonomy is centered on final natural-language responses. For chatbots that use tools or agentic actions, the same idea must extend to <strong>action variance</strong>. Evaluate the tool name, argument schema, argument values, call sequence, retries, side-effect class, and dependency on tool results. Two runs may produce the same final sentence while one silently calls a permission-changing tool and the other only gives instructions. For tools with side effects, action contract gates and action safety gates should run before textual semantic gates.

Consider the following example.

```text
Ground Truth: Refunds can be requested within 30 days of purchase.
Output A: You can request a refund within 30 days after buying the item.
Output B: Refunds can be requested within 60 days of purchase.
```

Output A differs in surface form, wording, and structure, but the meaning is essentially the same. Output B is textually close to the ground truth, but semantically dangerous. Exact match and edit distance alone cannot distinguish these cases correctly.

## 3. Do Not Treat “Same Meaning” as One Crude Bucket

One of the most dangerous shortcuts in LLM evaluation is to reduce semantic similarity to a single number.

Embedding cosine similarity is useful. It handles paraphrases, reordering, and wording differences well. But it can underweight local differences in negation, numbers, named entities, or conditions.

```text
A: This medication can be used during pregnancy.
B: This medication cannot be used during pregnancy.
```

The two sentences share most words and may be close in embedding space. Operationally, however, they say opposite things. Semantic variance should therefore be split into at least four relations.

| Relation | Meaning | Evaluation treatment |
|---|---|---|
| <strong>Bidirectional entailment</strong> | $g \Rightarrow y$ and $y \Rightarrow g$. Effectively equivalent | Usually acceptable |
| <strong>One-way entailment</strong> | One side contains the other. Summary, omission, or elaboration | Task-dependent |
| <strong>Contradiction</strong> | The two cannot both be true | Usually a serious failure |
| <strong>Neutral / unrelated</strong> | Neither entailment nor contradiction | Possible non-answer, topic drift, or unsupported addition |

Natural Language Inference (NLI) and LLM-as-judge can help with this distinction. They are not perfect. Numbers, units, dates, named entities, conditions, and exception clauses are common failure points. In high-stakes domains, extract entities and slots before making a broad semantic judgment.

For a refund-policy answer, for example, compare slots before comparing whole sentences.

| Slot | Ground Truth | Output |
|---|---|---|
| Window | 30 days | 60 days |
| Anchor date | Purchase date | Purchase date |
| Procedure | Can request | Can request |

Once the window slot differs, the answer fails regardless of how similar the overall sentence looks.

## 4. Choose Metrics by What They Observe

Evaluation metrics should be understood by their observation target, not by their prestige.

| Metric | Observation target | Good for | Weak for |
|---|---|---|---|
| Exact match | The raw string | Strict contracts, IDs, code, JSON | Paraphrases, notation variants |
| Normalized exact match | Normalized string | Whitespace, punctuation, casing, width differences | Semantic differences |
| Levenshtein distance | Character edits | Small notation differences, typos | Reordering, synonyms |
| Token F1 / n-gram | Word overlap | Keyword presence, short answers | Large paraphrases |
| ROUGE-L | Longest common subsequence | Structure and order similarity, summarization | Same meaning with reorganization |
| Embedding cosine similarity | Coarse semantic proximity | Paraphrases, expression differences | Numbers, negation, named entities |
| NLI | Entailment, contradiction, neutrality | Distinguishing equivalence, omission, contradiction | Long multi-claim text, specialized domains |
| LLM-as-judge | Rubric-based natural-language judgment | Composite quality, pragmatics, safety | Judge variance, bias, cost |
| Human evaluation | Human acceptability | Final quality, business context, subtle discomfort | Cost, rater differences, reproducibility |

These metrics are not a hierarchy. Cosine similarity is not simply “better” than ROUGE-L. LLM judgment is not always superior to exact match.

Metric values also depend on implementation details. For normalized exact match, decide how to handle casing, Unicode normalization, punctuation, whitespace, and width differences. Token F1, BLEU, and ROUGE-L depend on tokenization, which is especially important for Japanese and multilingual evaluation. To keep evaluation results comparable, log the normalizer, tokenizer, dictionary, and library versions.

For bank-transfer amount JSON, schema validation and exact comparison are strongest. For FAQ prose, embedding similarity and NLI are useful. For customer-service politeness, human evaluation or calibrated LLM-as-judge is necessary.

<strong>Good evaluation design is not choosing one powerful metric. It is arranging several weaker metrics in the right order, each catching a different failure mode.</strong>

## 5. A Decision Tree for Reading Differences Against Ground Truth

We can now build the decision tree practitioners often want: what should this output difference be called?

The input is a vector of metrics.

```text
raw_exact
normalized_exact
char_edit_distance
token_overlap
rouge_l
embedding_cosine
nli_g_to_y
nli_y_to_g
contradiction
slot_diff
speech_act_diff
safety_policy_diff
```

Read this vector from cheap checks to expensive ones.

To implement the tree, vague words such as “high,” “medium,” “low,” and “tiny” must become configuration.

| Item | What to fix |
|---|---|
| Normalizer / tokenizer | Unicode normalization, casing, width normalization, segmentation, dictionary, versions |
| Threshold | Cutoffs for edit distance, ROUGE-L, cosine, coverage, and so on |
| Precedence | Contract, safety, and forbidden-claim failures override high similarity scores |
| Action | Route to pass, fail, needs_review, or human_escalation |
| Calibration set | Human-labeled boundary cases used to choose thresholds |

For example, fail if a forbidden claim is detected even when cosine similarity is high. If ROUGE-L and cosine disagree and slot differences are unclear, route to `needs_review`. A decision tree should be managed as thresholds, precedence, and escalation rules, not as a purely intuitive taxonomy.

Tune thresholds on a calibration set, then report results on a separate frozen holdout or regression set. If you keep looking at the same evaluation set while adjusting thresholds, the evaluator itself overfits. For high-risk slices, track slice-level results on fixed sets, not only the global average.

### 5-1. Check the contract first

The first question is not semantic. It is whether the output satisfies the contract.

```text
if no_output or timeout:
  return "no response / execution failure"

if expected_json and not valid_json:
  return "format violation"

if required_language != detected_language:
  return "language constraint violation"

if length > budget:
  return "length constraint violation"
```

A contract violation can break the product regardless of meaning. If downstream code expects JSON, a semantically correct paragraph is still a failure.

### 5-2. Separate surface differences

Next, separate differences that disappear under normalization.

| Condition | Interpretation |
|---|---|
| raw exact = true | Perfect match |
| raw exact = false, normalized exact = true | Only whitespace, punctuation, casing, or notation differs |
| normalized exact = false, edit distance is tiny | Candidate typo, notation variant, or small unit-format difference |

Many cases end here. Whether “3,000 USD” and “3000 USD” should be considered different depends on the task. For payment execution, be strict. For explanatory FAQ text, normalization may be enough.

### 5-3. Separate structure from paraphrase

If the output is not surface-equivalent, token overlap and ROUGE-L tell us whether the structure remains close.

| Condition | Interpretation |
|---|---|
| High token overlap, high ROUGE-L, high cosine | Small paraphrase |
| Medium token overlap, low ROUGE-L, high cosine | Reordering, restructuring, larger paraphrase |
| Low token overlap, low ROUGE-L, high cosine | Semantically close but textually very different. Move to NLI before accepting |

ROUGE-L asks whether the same words appear in the same order. It is useful when order matters, such as procedures. It is too strict when bullet order is arbitrary.

### 5-4. Separate omission, addition, and contradiction

Even when two outputs seem semantically close, inspect information selection and propositional relations.

| Condition | Interpretation | Typical case |
|---|---|---|
| $g \Leftrightarrow y$ | Effectively equivalent | Large paraphrase |
| $y \Rightarrow g$ but $g \nRightarrow y$ | Output is more specific or adds information | Added caveat or example |
| $g \Rightarrow y$ but $y \nRightarrow g$ | Output is more general or omits information | Dropped condition, exception, or evidence |
| contradiction | Semantic conflict | Number mismatch, negation flip, condition mismatch |
| neutral | Non-answer, topic shift, or separate claim | Does not answer the question |

Omission is not always bad. In a short chat answer, omitting evidence may improve usability. In legal, medical, financial, or operational contexts, omitting an exception can cause harm.

If you use NLI, pay attention to direction. Standard NLI is an ordered premise/hypothesis classification, so one `nli_relation` label is not enough to distinguish equivalence, a more specific output, and a more general output. Evaluate at least both directions: `g -> y` and `y -> g`. If both entail, the texts are effectively equivalent. If only `y -> g` entails, the output is more specific or adds claims. If only `g -> y` entails, the output is more general or omits claims.

Information-selection variance is best measured as <strong>required-claim coverage</strong> and <strong>unsupported-claim intrusion</strong> rather than simply “more” or “less.”

```text
coverage = included_required_claims / all_required_claims
intrusion = unsupported_or_unwanted_claims / all_output_claims
```

Low coverage suggests omission. High intrusion suggests overgeneration or hallucination. In implementation, define the zero-denominator case when the output has no extracted claims, keep forbidden claims as hard gates rather than burying them inside an intrusion ratio, and consider severity-weighted claims. A refund deadline or contraindication should usually weigh more than an illustrative example.

Claim and slot extraction are themselves part of the evaluator, not perfect measurement primitives. If extraction is rule-based, version the schema and ontology. If it is model-based, measure extractor precision and recall against human-labeled claims. Store extraction confidence and audit borderline or high-severity claims. Extractor false negatives can hide real answer failures.

### 5-5. Inspect pragmatic differences

Finally, inspect differences that meaning alone cannot explain.

```text
Ground Truth: This action requires administrator permission. Ask an administrator.
Output A: This action requires administrator permission. Ask an administrator.
Output B: Let's try a way to bypass the permission check.
```

Output B may share many topical words with the reference. But as a conversational act, it suggests an unacceptable action. This is pragmatic variance.

Pragmatic variance includes the following.

| Type | Question |
|---|---|
| Refusal/answer variance | Does the system refuse when it should answer, or answer when it should refuse? |
| Next-action variance | Does it recommend a different next step? |
| Confidence variance | Does it overstate uncertainty or certainty? |
| Tone variance | Does politeness, empathy, expertise, or distance match the context? |
| Safety variance | Is the response allowed under policy? |

This layer often requires human evaluation or LLM-as-judge. Not every case needs human review. A practical system runs deterministic and semantic gates first, then samples pragmatic cases or focuses human review on high-risk areas.

## 6. Measure Direction, Not Only Magnitude

Many similarity metrics return a one-dimensional distance. Quality evaluation also needs direction: which way did the answer move?

The same numeric distance can mean different things.

```text
Ground Truth: Passwords must be at least 8 characters.
Output A: Passwords must be at least 12 characters.
Output B: Passwords must be at least 4 characters.
```

Both outputs changed the number. But A is stricter, while B is weaker. For security requirements, B is likely more dangerous. From a user-burden perspective, A may also be wrong.

Extract the direction of constraints.

| Ground Truth | Output | Direction | Interpretation |
|---|---|---|---|
| At least 8 chars | At least 12 chars | Stricter | Safer direction but spec mismatch |
| At least 8 chars | At least 4 chars | Weaker | Possible safety degradation |
| Within 30 days | Within 60 days | Broader allowance | Incorrectly expands refund rights |
| Within 30 days | Within 14 days | Narrower allowance | Incorrectly restricts user rights |

The same applies to pragmatics. Did refusal become stronger or weaker? Did confidence increase or decrease? Did the system push the user to act or ask them to pause?

Variance evaluation becomes easier if every difference is described with three attributes.

| Attribute | Question | Examples |
|---|---|---|
| magnitude | How different is it? | Edit distance, similarity, claim-diff count |
| type | What changed? | Surface, structure, omission, contradiction, refusal |
| direction | Which way did it move? | Stricter, weaker, more certain, more cautious, over-refusal |

Acceptability depends on the combination of all three.

## 7. Human Acceptability Is a Composition of Scores

The quality of an output $y$ against ground truth $g$ can be represented as a vector rather than a single score.

$$
q(y, g) = [C_0, S_1, L_2, R_3, I_4, M_5, P_6]
$$

$C_0$ is contract quality, $S_1$ surface quality, $L_2$ lexical quality, $R_3$ structural quality, $I_4$ information-selection quality, $M_5$ semantic quality, and $P_6$ pragmatic quality.

Human acceptability is plausibly a nonlinear function of this vector.

$$
acceptable = f(C_0, S_1, L_2, R_3, I_4, M_5, P_6, task\_risk)
$$

$task\_risk$ represents domain risk. In casual conversation, lexical and structural variance often do not matter. In FAQ answers, information selection and semantics matter. In finance, medicine, law, or security, small changes in numbers, conditions, or refusal policy may be unacceptable.

In practice, it is better to use gates than a single global threshold.

| Gate | Failure condition | Treatment |
|---|---|---|
| Contract gate | No response, invalid format, missing required fields | Automatic fail |
| Safety gate | Policy violation, unsafe action, PII leakage | Automatic fail or human review |
| Semantic gate | Missing required claim, contradiction, important slot mismatch | Usually fail; review for low-risk tasks |
| Information-selection gate | Missing evidence, overgeneration, unsupported inference | Task-dependent |
| Experience gate | Verbose, cold, vague, over-refusal | Sample evaluation or A/B evaluation |

This design allows harmless paraphrases that exact match would reject. It also rejects textually similar but semantically dangerous answers.

## 8. How to Aggregate Variance Between Outputs

In addition to comparing each output with ground truth, we need to measure output-to-output variance under fixed conditions. If 9 out of 10 runs are correct and one run is dangerous, the average score may look high. In production, however, that one output can reach a user.

Useful aggregation metrics include:

| Metric | Meaning | Use case |
|---|---|---|
| Pass rate | How many of $n$ runs pass the gates | Most important stability measure |
| Worst-case score | Quality of the worst output | High-risk domains |
| Mean pairwise distance | Average distance between outputs | Surface and wording dispersion |
| Cluster count | Number of semantic clusters | Detecting mixed answer policies |
| Contradiction rate | Fraction of output pairs that contradict | Knowledge or policy instability |
| Refusal flip rate | Fraction of runs where refusal/answer changes | Safety and over-refusal evaluation |

The pass-rate distribution is especially important.

Do not collapse pass rate into one global number across heterogeneous cases. `920/1000 pass` can look good while hiding a broken high-risk slice such as permissions, medicine, refunds, or security policy. Report per-case pass rates, per-slice pass rates, macro averages, risk-weighted summaries, and worst-slice results. Confidence intervals or bootstraps should consider clustering by case or slice, not only by generation.

There is a statistical trap here too. The $n(n-1)/2$ pairs produced from $n$ outputs are not independent observations because each output participates in many pairs. Do not treat the pair count as the independent sample size when reporting contradiction-rate uncertainty. Safer reporting defines the distance metric, clustering method, and threshold, then bootstraps over outputs if needed. Also report per-output indicators such as “share of outputs that contradict at least one other output.” Cluster count likewise depends heavily on the metric and threshold, so interpret it together with the configuration.

```text
Case A: 10/10 pass, expression varies only stylistically
Case B: 8/10 pass, two runs omit a required condition
Case C: 9/10 pass, one run suggests an unsafe action
```

Average similarity may not separate A, B, and C clearly. Operationally, they are very different. A is usually acceptable. B points to prompt or retrieval-context improvement. C may require a safety gate or deployment stop.

Clustering outputs can also reveal the model's uncertainty.

```text
Cluster 1: Says the refund is allowed
Cluster 2: Says the refund is not allowed
Cluster 3: Tells the user to contact support
```

If these clusters appear under the same condition, the issue is not mere expressive diversity. Knowledge, policy, retrieval grounding, or prompt constraints are unstable.

## 9. Build Evaluation Sets Around Places Where Variance Matters

Randomly collected questions rarely expose the dangerous parts of variance. Evaluation sets should intentionally include boundary cases where models tend to waver.

| Case type | Purpose |
|---|---|
| Questions with many valid paraphrases | Check whether harmless paraphrases are accepted |
| Questions with numbers, dates, and units | Detect local semantic variance |
| Policy questions with conditions and exceptions | Detect omission and overgeneralization |
| Questions near refusal boundaries | Measure refusal/answer variance |
| Questions requiring multiple evidence points | Measure information-selection variance |
| Questions with long conversation history | Measure context-retention variance |
| Questions matching several similar FAQs | Measure retrieval and evidence-selection variance |

For such cases, ground truth should not be only a model answer. A single natural-language reference rejects too many valid alternatives.

A better ground truth has several layers.

| Ground-truth layer | Content | Example |
|---|---|---|
| Contract | Output format, language, length, required fields | JSON schema, English, under 200 words |
| Required claims | Meaning units that must appear | Window is 30 days; anchor is purchase date |
| Forbidden claims | Things the answer must not say | 60 days, unconditional refund, bypass permission |
| Desired pragmatics | Tone, confidence, next action | Avoid overclaiming; route to support when needed |

A reference answer is only one realization of this ground truth.

Ground truth also needs provenance. For RAG, FAQ, policy, and legal-style tasks, required and forbidden claims should carry source ID, quoted source span, effective date, claim weight, allowed paraphrases, annotator, adjudicator, and review status. High-risk claims should use dual annotation or spot-checked adjudication. If ground truth cannot be traced to who decided what from which source version, evaluation merely replaces model uncertainty with another unversioned opinion.

For RAG systems, also evaluate answer-side grounding. Each material output claim should link to retrieved source spans. Report unsupported-claim rate, citation precision, citation recall, and source-version mismatches. An answer can contain the right claim but cite the wrong document, which is still a failure for auditability and user trust.

## 10. If You Use LLM-as-Judge, Measure Judge Variance Too

LLM-as-judge is extremely useful for variance evaluation. It is especially helpful for pragmatics, tone, safety, and composite acceptability judgments that would otherwise require expensive human review.

But LLM-as-judge does not make the evaluation problem disappear. A generative model used as a judge has its own variance.

At minimum, measure the following.

| Check | Method |
|---|---|
| Agreement with humans | Label a sample with humans and inspect the judge confusion matrix |
| Inter-judge agreement | Use multiple judges or repeated judgments |
| Position bias | Swap A/B order in pairwise comparisons |
| Verbosity bias | Check whether longer answers receive unfairly higher scores |
| Self-preference | Check whether outputs from a related model family are favored |
| Threshold stability | Inspect whether borderline cases flip labels |

Raw agreement is not enough. On imbalanced data, a judge can look accurate by saying almost everything passes. For semantic and safety gates, inspect the confusion matrix by failure class, precision and recall for `fail`, and the false-negative rate for severe failures. Use adjudicated human labels for high-risk slices. Also log judge model/version/fingerprint, judge prompt, rubric version, temperature/seed, and JSON parser or post-processor version as evaluation conditions.

Prefer prompts that separate labels from evidence.

```text
You are evaluating whether the assistant answer is acceptable.
Assess only the following rubric items:
1. Required claims are present.
2. No forbidden claims are present.
3. The answer does not contradict the reference.
4. The recommended next action is safe.

Return JSON with:
- pass: boolean
- failed_items: string[]
- evidence: short quotes from the answer
```

Do not treat the judge's explanation as truth. It is an audit trail, not proof that the judgment is correct.

## 11. A Practical Evaluation Pipeline

A production-oriented evaluation pipeline can run in this order.

```text
1. Freeze logs
   model, parameters, prompts, retrieval snapshot, tool outputs,
   session state, memory, user profile, clock/timezone, cache, side-effect state,
   judge/extractor/reranker versions and prompts

2. Contract checks
   no output, timeout, schema, language, length

3. Normalization and surface comparison
   exact, normalized exact, edit distance

4. Structural comparison
   token overlap, ROUGE-L, outline/order comparison

5. Claim / slot extraction
   required claims, forbidden claims, numeric/entity slots

6. Semantic relation judgment
   NLI, QA-based check, calibrated LLM judge

7. Pragmatic and safety judgment
   refusal, next action, tone, policy, sampled human review

8. Aggregation
   pass rate, worst case, variance, clusters, contradiction rate
```

The order matters because cheap and reproducible checks should run first. There is no need to call an LLM judge on broken JSON. There is no need to debate embedding similarity when a required numeric slot clearly differs.

An evaluation report should show actionable failure modes, not just average scores.

| Case | Pass rate | Main failure layer | Worst example | Improvement |
|---|---|---|---|---|

This is far more actionable than saying “the model scored 0.82.”

## 12. Conclusion: Variance Is Not Something to Eliminate, but Something to Manage

LLM output variance is not merely noise. Natural language allows multiple correct realizations, and expressive diversity is often valuable. The problem is not to eliminate all variance. The problem is to <strong>separate acceptable variance from unacceptable variance</strong>.

Exact match alone is not enough. Embedding similarity alone is not enough. LLM-as-judge alone is not enough.

This article classified variance into seven layers.

1. Layer 0 contract variance: existence, format, or constraints change
2. Layer 1 surface variance: characters or notation change
3. Layer 2 lexical variance: words or phrases change
4. Layer 3 structural variance: order, paragraphs, or reasoning flow change
5. Layer 4 information-selection variance: claims or evidence change
6. Layer 5 semantic variance: propositions, relations, or truth conditions change
7. Layer 6 pragmatic variance: speech act, stance, or safety implications change

The important point is that lower layers are easier to measure mechanically, while higher layers are closer to human acceptability.

When humans decide whether an answer is acceptable, they are not checking string similarity alone. They ask whether the meaning is preserved, whether required conditions are present, whether the next action is safe, and whether the response is appropriately cautious for the task risk.

The job of evaluation design is to decompose that judgment, make as much of it reproducible as possible, and reduce the amount of human review needed.

Quality assurance for LLM chatbots should move from “how similar is this one answer to the reference?” to “does the output distribution under fixed conditions stay within the range acceptable for this task?”

Variance will not disappear. That is exactly why we need to make it measurable.
