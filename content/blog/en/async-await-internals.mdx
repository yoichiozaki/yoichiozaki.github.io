## What async/await Hides

Many languages, including JavaScript, Python, Rust, and C#, use `async/await` as the syntax for writing asynchronous code. The syntax looks similar, but the machinery behind it differs widely between languages and runtimes.

```javascript
async function fetchData() {
  const response = await fetch("/api/data");
  const json = await response.json();
  return json;
}
```

When this code runs, the runtime does the following:

1. At `await`, it <strong>suspends</strong> the function and returns control to the runtime
2. It watches for I/O completion without blocking the thread
3. When the I/O completes, it <strong>resumes</strong> the function where it left off
4. Meanwhile, it schedules and runs other async operations

The sections below cover three execution models in turn: JavaScript's event loop, Python's asyncio, and Rust's poll-based Futures.

## Prerequisites: Sync, Async, Concurrent, Parallel

These four terms are often confused, so here is what each one means.

| Term | Meaning |
|------|---------|
| Synchronous | Blocks and waits until the operation completes |
| Asynchronous | Starts the operation and moves on; gets notified upon completion |
| Concurrent | Multiple tasks have overlapping execution periods (possible on a single core) |
| Parallel | Multiple tasks physically execute simultaneously (requires multiple cores) |

async/await provides <strong>concurrency</strong>; it does not necessarily run anything in parallel. JavaScript's async/await, for example, makes progress on several operations on a single thread.

## JavaScript: The Event Loop Model

### Event Loop Structure

JavaScript code runs on a single thread. The <strong>event loop</strong> is what lets that one thread handle many asynchronous operations.

Four components are involved in how the event loop works:

1. <strong>Call Stack</strong> — Stack of currently executing functions
2. <strong>Web APIs / Node APIs</strong> — Environment for async operations (timers, network, file I/O)
3. <strong>Microtask Queue</strong> — Promise `.then` / `.catch` / `.finally` callbacks, `queueMicrotask()`
4. <strong>Macrotask Queue</strong> (Task Queue) — `setTimeout`, `setInterval`, I/O callbacks, UI events

<EventLoopCycle />

### Event Loop Execution Order

One turn of the browser event loop proceeds in this order:

1. Dequeue and execute one task (the initial script, a timer callback, an input event, etc.)
2. When that task's call stack becomes empty, run the microtask checkpoint: drain Promise jobs / `queueMicrotask()` callbacks until the queue is empty
3. Update rendering if needed
4. Return to step 1 and pick the next task

Because of this order, <strong>microtasks do not interrupt the running task, but the microtask queue is drained before the next task starts</strong>. In the code below, the Promise callback (a microtask) runs before the `setTimeout` callback (a task).

```javascript
console.log("1");             // synchronous

setTimeout(() => {
  console.log("4");           // macrotask
}, 0);

Promise.resolve().then(() => {
  console.log("3");           // microtask
});

console.log("2");             // synchronous

// Output order: 1, 2, 3, 4
```

### async/await Transformation

`async/await` is often described as syntactic sugar over Promises. In practice the engine saves the function's execution state and suspends and resumes it, but conceptually it behaves like the following Promise chain:

```javascript
// Code written with async/await
async function example() {
  console.log("A");
  const result = await fetchData();
  console.log("B");
  return result;
}

// Conceptual internal transformation
function example() {
  console.log("A");
  return fetchData().then((result) => {
    console.log("B");
    return result;
  });
}
```

When an `await` expression is reached, the engine does the following:

1. Evaluate the right-hand side expression; if the value is not a Promise, wrap it in a resolved Promise
2. Register the rest of the function to run when that Promise resolves (on resolution, the resume step enters the microtask queue)
3. Suspend the function and return control to the caller

As a result, the event loop can keep processing other tasks while the I/O is pending.

### V8 Engine Optimizations

V8 (the JavaScript engine in Chrome and Node.js) made `await` faster in v7.2. When the value passed to `await` is already a native Promise, `promiseResolve` now uses that Promise as is, and V8 no longer creates an extra wrapper Promise or the `throwaway` Promise. This cut the number of microtask ticks for one `await` from 3 to 1.

## Python: asyncio and Coroutines

### Python Coroutines

Python's `async/await` was introduced in Python 3.5 and is based on <strong>coroutines</strong>. A coroutine is a function whose execution can be suspended and resumed; Python builds coroutines on an extension of the generator mechanism.

```python
import asyncio

async def fetch_data():
    print("fetch start")
    await asyncio.sleep(1)  # Simulates I/O operation
    print("fetch done")
    return 42
```

Calling a function defined with `async def` doesn't run its body; it returns a coroutine object.

```python
coro = fetch_data()   # Function body has NOT run yet!
print(type(coro))      # <class 'coroutine'>
```

An event loop (runtime) is needed to actually execute the coroutine.

### asyncio Event Loop

Python's `asyncio` module provides an event loop implementation. In JavaScript the runtime already has an event loop running; in Python you have to create and run one explicitly, for example with `asyncio.run()`:

```python
import asyncio

async def main():
    result = await fetch_data()
    print(result)

# Create and run the event loop
asyncio.run(main())
```

The asyncio event loop relies on three mechanisms:

1. <strong>I/O multiplexing</strong>: On Unix, `SelectorEventLoop` uses selector backends such as `epoll` and `kqueue`; on Windows, the default `ProactorEventLoop` uses IOCP rather than the selector API
2. <strong>A queue of ready callbacks</strong>: The event loop puts callbacks that can run immediately into a queue and runs them one at a time
3. <strong>Tasks</strong>: An `asyncio.Task` wraps a coroutine and puts a callback that advances the coroutine by one step into this queue. When the Future the coroutine is waiting on completes, the next step is queued again

### Internal Implementation of Python Coroutines

Python's native coroutines (`async def`) are a distinct type from generators, but in CPython's implementation they share the same suspension machinery (`YIELD_VALUE` opcode) as generators. `await` uses the `__await__` protocol and conceptually works like this:

```python
# Conceptual internal behavior
async def example():
    result = await some_coroutine()
    print(result)

# Internally (simplified):
# 1. Call some_coroutine() to get a coroutine object
# 2. Advance execution with .send(None)
# 3. When the coroutine suspends, return control to the event loop
# 4. After I/O completion, pass the result with .send(result) to resume
```

In CPython's implementation, the coroutine frame (local variables, execution position, etc.) is kept on the heap, so suspending and resuming does not require unwinding or restoring the stack.

### asyncio Constraints and the GIL

Python's `asyncio` has the following constraints:

- <strong>GIL (Global Interpreter Lock)</strong>: In CPython, only one thread executes Python bytecode at a time. asyncio runs on a single thread, so the GIL barely affects it
- <strong>Not suited for CPU-bound work</strong>: async/await helps with work that spends much of its time waiting on I/O. For CPU-bound work, use `multiprocessing` or `concurrent.futures.ProcessPoolExecutor`
- <strong>Library support required</strong>: Calling a synchronous library (e.g., `requests`) directly from async code blocks the event loop, so you need an async alternative (e.g., `aiohttp`)

## Rust: Zero-Cost Futures and Polling

### Rust's Async Model

Rust's async/await differs from JavaScript and Python in three ways:

1. <strong>The runtime is not built into the language</strong> — you choose a third-party runtime such as tokio or smol
2. <strong>Futures are poll-based</strong> — instead of a callback announcing completion, the runtime asks the Future whether it has finished
3. <strong>Zero-cost abstraction</strong> — async/await adds almost no overhead compared with writing the state machine by hand

### The Future Trait

Rust's Future is defined by this trait:

```rust
pub trait Future {
    type Output;
    
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}

pub enum Poll<T> {
    Ready(T),    // Complete: return the result
    Pending,     // Not yet complete: poll me again later
}
```

JavaScript's Promises and Python's coroutines are <strong>push-based</strong>: the side that completes calls a callback to announce it. Rust is <strong>pull-based (polling)</strong>: the runtime asks the Future whether it has finished.

### State Machine Transformation

Rust's compiler transforms `async fn` into a state machine.

```rust
async fn example() -> i32 {
    let a = fetch_a().await;  // Suspension point 1
    let b = fetch_b().await;  // Suspension point 2
    a + b
}

// State machine generated by the compiler (conceptual):
enum ExampleFuture {
    Start,
    WaitingA { future_a: FetchAFuture },
    WaitingB { a: i32, future_b: FetchBFuture },
    Done,
}

impl Future for ExampleFuture {
    type Output = i32;
    
    fn poll(self: Pin<&mut Self>, cx: &mut Context) -> Poll<i32> {
        loop {
            match self.state {
                Start => {
                    self.future_a = fetch_a();
                    self.state = WaitingA;
                }
                WaitingA => {
                    match self.future_a.poll(cx) {
                        Poll::Ready(a) => {
                            self.a = a;
                            self.future_b = fetch_b();
                            self.state = WaitingB;
                        }
                        Poll::Pending => return Poll::Pending,
                    }
                }
                WaitingB => {
                    match self.future_b.poll(cx) {
                        Poll::Ready(b) => {
                            return Poll::Ready(self.a + b);
                        }
                        Poll::Pending => return Poll::Pending,
                    }
                }
                Done => panic!("polled after completion"),
            }
        }
    }
}
```

This transformation has the following properties:

- <strong>No mandatory per-`await` heap allocation</strong>: The Future is a concrete state-machine value that can stay on the stack when awaited directly; it is heap-allocated when you box it, erase its type, or spawn it into a runtime task
- <strong>No dynamic dispatch</strong>: Concrete types are determined at compile time
- Each `await` corresponds to one state transition

### Waker and Runtime Cooperation

In the poll-based model, the runtime needs some way to learn when to poll a Future again. That mechanism is the <strong>Waker</strong>:

```rust
// Context contains a Waker
pub struct Context<'a> {
    waker: &'a Waker,
}
```

Before a Future returns `Poll::Pending`, it stores a clone of the Waker with the runtime's reactor/driver while that driver registers OS readiness interest (for example with epoll/kqueue/IOCP). When the OS reports readiness, the driver calls the Waker, telling the runtime to poll this Future again.

```text
1. Runtime calls Future.poll()
2. Future initiates I/O internally; the runtime driver registers OS readiness and stores the Waker
3. Returns Poll::Pending
4. Runtime polls other Futures
5. I/O becomes ready -> the runtime driver wakes the task via the Waker
6. Runtime polls that Future again
7. Returns Poll::Ready(result)
```

### The tokio Runtime

tokio is the most widely used async runtime in Rust.

```rust
#[tokio::main]
async fn main() {
    let result = fetch_data().await;
    println!("{result}");
}
```

tokio's main components are:

- <strong>Multi-threaded scheduler</strong>: A work-stealing algorithm distributes tasks across CPU cores
- <strong>I/O driver</strong>: Async I/O wrapping epoll/kqueue/IOCP
- <strong>Timer</strong>: Hierarchical timer wheel
- <strong>Single-threaded mode</strong>: With `#[tokio::main(flavor = "current_thread")]`, tokio runs as a single-threaded event loop

## Cross-Language Comparison

<AsyncComparison />

### Push vs Pull

| Model | Languages | Mechanism | Advantage |
|-------|-----------|-----------|-----------|
| Push-based | JS, Python | Calls callback/continuation on completion | Simpler mechanism |
| Pull-based | Rust | Runtime polls Futures | Zero-cost, natural cancellation |

One advantage of the pull-based model is how easy cancellation is. In Rust, dropping a Future means it is never polled again, so its work stops (a task spawned onto a runtime, however, keeps running even if you drop its JoinHandle). Push-based models often need an explicit way to signal cancellation, such as JavaScript's `AbortController`.

### Memory Model

| Language | Coroutine State Storage | Memory Allocation |
|----------|------------------------|-------------------|
| JavaScript | Suspended function state (V8 heap) | GC-managed |
| Python | Coroutine frame (heap) | GC-managed |
| Rust | State machine (stack or Box) | Manually controllable |
| Go | Goroutine stack (contiguous, growable) | GC-managed + stack growth |

### The Function Coloring Problem

Many languages draw a clear line between sync and async functions, which leads to the "<strong>function coloring problem</strong>":

- Inside a sync function you cannot `await` an async function's result (to wait for it, you must block the thread or start an event loop, as `asyncio.run()` does)
- An async function can call sync functions, but calling one that blocks for a long time stalls the event loop

```python
# NG: Can't directly call async from sync
def sync_function():
    result = await async_function()  # SyntaxError!

# OK: Bridge with asyncio.run()
def sync_function():
    result = asyncio.run(async_function())
```

Go has no async/await and so does not have this problem. Any function can be started as a new goroutine with the `go` keyword, and while a goroutine waits on I/O, the runtime runs other goroutines.

## Practical Pitfalls

### JavaScript Pitfalls

```javascript
// NG: Forgetting await returns a Promise object
async function bad() {
  const data = fetch("/api");  // Missing await!
  console.log(data);            // Prints Promise object
}

// NG: Sequential when it could be parallel
async function sequential() {
  const a = await fetchA();  // Wait 1 second
  const b = await fetchB();  // Wait 1 more second → 2 seconds total
}

// OK: Use Promise.all for parallel execution
async function parallel() {
  const [a, b] = await Promise.all([fetchA(), fetchB()]);  // 1 second total
}
```

### Python Pitfalls

```python
# NG: Blocking I/O inside async code
async def bad():
    import requests
    response = requests.get("https://example.com")  # Blocks the event loop!

# OK: Use async libraries
async def good():
    import aiohttp
    async with aiohttp.ClientSession() as session:
        response = await session.get("https://example.com")

# Running independent tasks concurrently
async def gather_example():
    results = await asyncio.gather(
        fetch_a(),
        fetch_b(),
        fetch_c(),
    )
```

### Rust Pitfalls

```rust
// NG: Blocking operation inside async fn
async fn bad() {
    std::thread::sleep(Duration::from_secs(1)); // Blocks the runtime thread!
}

// OK: Use tokio's async version
async fn good() {
    tokio::time::sleep(Duration::from_secs(1)).await;
}

// OK: Use spawn_blocking for CPU-bound work
async fn cpu_work() {
    let result = tokio::task::spawn_blocking(|| {
        heavy_computation()
    }).await.unwrap();
}
```

## Summary

The async/await syntax looks similar across languages, but the implementations behind it differ widely:

- <strong>JavaScript</strong>: Suspends and resumes functions using Promises on a single-threaded event loop. The priority of microtasks over macrotasks determines execution order
- <strong>Python</strong>: The asyncio event loop schedules coroutines (an extension of generators). Under the GIL, it makes progress on I/O waits concurrently
- <strong>Rust</strong>: Compiles async fn into Future state machines. The runtime drives execution by polling, and no heap allocation is required per `await`

All three share one design goal: <strong>don't leave a thread idle while waiting on I/O</strong>. async/await is syntax that lets you write this kind of asynchronous code in a form close to synchronous code.
