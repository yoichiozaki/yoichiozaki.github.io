## はじめに —— LLM の「正しさ」は 1 回の出力では測れない

LLM をバックエンドにしたチャットボットは、いま急速にプロダクトの表面へ出てきている。カスタマーサポート、社内ナレッジ検索、ドキュメント作成支援、開発者向けエージェント、音声アシスタント。多くの場面で、ユーザーは「モデル」ではなく <strong>モデルの出力を含む会話システム</strong> を使う。

このとき応答品質をどう評価するか。従来のソフトウェアなら、同じ入力に対して同じ出力が返ることを前提にテストを書ける。しかし LLM は違う。モデル、パラメタ、システムプロンプト、ユーザープロンプト、検索結果、ツール定義を固定しても、出力は完全には固定されないことがある。

ある回では丁寧に箇条書きで答える。次の回では同じ意味を短く述べる。別の回では一部の根拠を省略する。さらに悪い場合、数値・固有名詞・結論の向きが変わる。

この記事では、この現象を次のように定義する。

> <strong>ブレ</strong>：生成条件を同一にしたとしても発生する生成結果の差異。
>
> <strong>ドリフト</strong>：生成条件の変化によって発生する生成結果の差異。

ここでいう生成条件には、利用モデル、モデルバージョン、推論パラメタ、システムプロンプト、ユーザープロンプト、ツール定義、検索インデックスのスナップショット、参照文書、実行時ポリシー、バックエンドの system fingerprint などが含まれる。つまり「今日はモデルが更新された」「検索結果が変わった」「プロンプトを書き換えた」による差分は、本稿ではブレではなくドリフトとして扱う。

もちろん実務では、両者は簡単には分離できない。API の背後でモデルが更新されれば、観測上はブレに見えても実体は隠れたドリフトかもしれない。だから評価ログには、できる限りモデル ID、バージョン、推論パラメタ、seed、プロンプト、検索結果、ツール応答、system fingerprint、セッション状態、メモリ、ユーザープロファイル、時刻・タイムゾーン、キャッシュ状態、副作用を持つ外部状態、ランタイムの識別子を残す必要がある。

seed を使える環境では、評価モードを 2 つに分けると混乱が減る。

| モード | 固定するもの | 何を測るか |
|---|---|---|
| <strong>ブレ測定</strong> | モデル、プロンプト、検索・ツール状態、推論パラメタ、観測された model revision / system fingerprint。seed は未指定または独立に記録 | 同一条件下で現れる確率的な出力分布 |
| <strong>再現性リプレイ</strong> | 上記に加えて seed と system fingerprint も固定 | ほぼ同じ出力を再現できるか。差分が出たら隠れた非決定性やドリフトを疑う |

同じ seed を固定した反復は、モデルの確率的な出力分布をサンプリングしているというより、再現性やバックエンド非決定性をテストしている。両者を混ぜると、ブレの評価値を読み違える。

ブレ測定でも、観測された fingerprint が変わった実行を同じ母集団に混ぜるべきではない。fingerprint が変わったら、隠れたドリフトとして分けるか、別 strata として分析する。

本稿の主張はシンプルだ。

<strong>LLM 応答の許容可能性は、1 つの類似度スコアでは決まらない。契約・表層・語彙・構造・情報選択・意味・語用という複数のブレの程度の組み合わせで決まる。</strong>

完全一致だけを見れば、 harmless な言い換えまで失敗扱いになる。埋め込み類似度だけを見れば、数値や否定の反転を見落とす。LLM 判定だけに頼れば、評価者自身のブレを品質評価に混ぜてしまう。

必要なのは、ブレを「なんとなく違う」と言わず、何が違うのかを層に分けて測ることだ。

## 1. 評価対象を「1 出力」から「出力分布」へ移す

生成条件を $c$、プロンプトまたは評価ケースを $p$ とする。同じ $c$ と $p$ で $n$ 回生成した出力を、次のように置く。

$$
Y_{p,c} = \{ y_1, y_2, \ldots, y_n \}
$$

従来のテストは、単一の出力 $y$ と Ground Truth $g$ を比べる発想になりがちだ。しかしブレを評価するなら、見るべきものは $y$ ではなく <strong>同一条件下の出力分布</strong> である。

この分布に対して、少なくとも 2 種類の比較がある。

| 比較 | 問い | 例 |
|---|---|---|
| <strong>対 Ground Truth 比較</strong> | 各出力は期待回答からどれくらい離れているか | 正解文、期待 JSON、評価ルーブリックとの比較 |
| <strong>出力間比較</strong> | 同一条件の出力同士はどれくらい散らばっているか | $y_i$ と $y_j$ のペア比較、クラスタ数、pass/fail の散らばり |

対 Ground Truth 比較だけでは、「たまたま 1 回だけ良かった」のか「安定して良い」のかが分からない。出力間比較だけでは、「安定して間違っている」ケースを見逃す。したがって、ブレ評価は <strong>正解からの距離</strong> と <strong>同一条件内の散らばり</strong> を同時に見る必要がある。

最小限の評価プロトコルは次のようになる。

1. 評価ケース $p$ と生成条件 $c$ を固定する。
2. 同じケースを $n$ 回実行する。実務上はコストに応じて $n=5$ から $30$ 程度のスクリーニングから始める。
3. すべての出力を保存する。最終テキストだけでなく、ツール呼び出し、検索結果、拒否理由、トークン使用量、レイテンシも残す。
4. 各出力を Ground Truth と比較する。
5. 出力同士を相互比較する。
6. 平均だけでなく、最悪値、分位点、合格率、クラスタ数を見る。

$n=5$ から $30$ は、精密な信頼性推定ではなく、危険なブレを早期に見つけるための探索的な範囲である。合格率は必ず `pass_count / n` の形で分母と一緒に報告し、Wilson 区間や Jeffreys 区間のような二項比率の不確実性も併記するのが望ましい。ただし、この区間は「固定した二値ゲートに対する試行が実質的に独立した Bernoulli 試行である」という近似に依存する。実際の LLM API では、キャッシュ、共有バックエンド状態、レート制限、judge の使い回しによって試行が相関することがある。

リリース判定に使うなら、事前に「下側信頼限界が 0.95 を超えること」や「失敗率の上側限界が 1% 未満であること」のような基準を決める。30/30 の成功でさえ、稀な失敗がないことを証明しない。独立 Bernoulli 近似でも、30 回無失敗の片側 95% 上側失敗率はおおよそ 10% 程度に残る。高リスクの安全ゲートや意味ゲートでは、少数試行の 9/10 や 29/30 を「安定」と読みすぎず、より大きなサンプルと境界ケースの集中テストを用意する。

目安として、独立試行で失敗が 0 件だったときに片側 95% の上側失敗率を 1% 未満にしたいなら、$n \ge \log(0.05) / \log(0.99)$、つまり約 299 回の無失敗が必要になる。これは「本番安全性を証明する」には少数サンプルがいかに弱いかを示すための概算であり、実務ではスライス別のリスクや試行相関も考慮する。

ここで重要なのは、ブレを「悪」と決めつけないことだ。自然言語には複数の正しい答えがある。説明文であれば、表現の多様性はむしろ望ましい場合もある。一方、医療判断、契約条項、見積金額、権限操作では、小さなブレが重大なリスクになる。ブレの許容量は、タスクによって変わる。

## 2. ブレの分類 —— 何が変わったのかを分ける

ブレは 1 つの現象ではない。文字が違うのか、語順が違うのか、情報の選び方が違うのか、意味が違うのか、会話上の行為が違うのかで、品質への影響はまったく異なる。

本稿では、ブレを次の 7 層に分ける。

| 層 | ブレの種類 | 変化するもの | 典型例 | 主な計測 |
|---|---|---|---|---|
| 0 | <strong>契約ブレ</strong> | 出力の存在・形式・制約 | 空応答、JSON 不正、言語違い、長さ超過 | スキーマ検証、正規表現、言語判定、長さ |
| 1 | <strong>表層ブレ</strong> | 文字・表記 | 全角半角、句読点、改行、表記ゆれ | 完全一致、正規化一致、編集距離 |
| 2 | <strong>語彙ブレ</strong> | 語・句 | 「購入」と「買う」、「削除」と「消去」 | token F1、n-gram、BLEU、chrF |
| 3 | <strong>構造ブレ</strong> | 順序・段落・論理展開 | 箇条書き順序の入れ替え、結論先出し/後出し | ROUGE-L、LCS、依存構造、アウトライン比較 |
| 4 | <strong>情報選択ブレ</strong> | 含まれる事実・根拠・詳細度 | 根拠の省略、注意事項の追加、例の有無 | slot/claim 抽出、coverage、precision/recall |
| 5 | <strong>意味ブレ</strong> | 命題・関係・真偽条件 | 数値違い、否定の反転、原因と結果の入れ替え | 埋め込み類似度、NLI、QA 評価、LLM 判定 |
| 6 | <strong>語用ブレ</strong> | 会話行為・態度・リスク | 拒否/回答の差、推奨行動の差、確信度の差 | ルーブリック、人間評価、LLM-as-judge、方針分類 |

この表で注意したいのは、1 つの出力ペアが複数の層で同時に違いうることだ。大幅な言い換えは、文字も語彙も構造も変える。誤った数値は、表層的には小さな差でも意味的には大きな差になる。

したがって、MECE に近づける対象は「応答ペアに 1 個だけ貼るラベル」ではなく、<strong>観測する側面</strong> である。各層は「主に何を観測しているか」を分けるための診断次元であり、実際の失敗は複数層にまたがりうる。たとえば必須 claim の欠落は情報選択ブレであると同時に、タスクによっては意味の不完全性でもある。安全でない推奨は語用ブレとして観測できるが、安全ゲートでは独立に拒否される。最終判定では、単一ラベルに押し込まず、各層のスコアをベクトルとして組み合わせる。

また、本稿の分類は最終的な自然言語応答を中心にしている。ツール実行やエージェント行動を含むチャットボットでは、同じ考え方を <strong>行動ブレ</strong> に拡張する必要がある。見るべき対象は、呼び出したツール名、引数スキーマ、引数値、呼び出し順序、リトライ、外部副作用の種類、ツール結果への依存関係である。たとえば「同じ回答文」でも、裏側で権限変更ツールを呼んだ場合と、単に案内文を返した場合は同じ品質とは扱えない。副作用を持つツールでは、テキストの意味ゲートより前に、行動の契約ゲートと安全ゲートを置くべきである。

たとえば、次の 2 つの回答を考える。

```text
Ground Truth: 返金は購入日から30日以内に申請できます。
Output A: 購入後30日以内であれば返金申請が可能です。
Output B: 返金は購入日から60日以内に申請できます。
```

Output A は表層・語彙・構造が違うが、意味はほぼ同じである。Output B は文字列としては Ground Truth にかなり近いが、意味は危険に違う。完全一致や編集距離だけでは、この差を正しく扱えない。

## 3. 「同じ意味」を雑に扱わない

LLM 評価で最も危険なのは、「意味が近い」を 1 つの数値で片づけることだ。

埋め込みのコサイン類似度は便利である。大幅な言い換え、順序違い、語彙違いに強い。しかし、似た文脈にいる否定・数値・固有名詞の違いを過小評価することがある。

```text
A: この薬は妊娠中に使用できます。
B: この薬は妊娠中に使用できません。
```

この 2 文は語彙の大半を共有し、埋め込み空間でも近くなりやすい。しかし実務上は真逆である。したがって、意味ブレは少なくとも次の 4 種類に分けて見るべきだ。

| 意味関係 | 説明 | 評価上の扱い |
|---|---|---|
| <strong>双方向含意</strong> | $g \Rightarrow y$ かつ $y \Rightarrow g$。実質同義 | 許容しやすい |
| <strong>片方向含意</strong> | 片方がもう片方を含む。要約・省略・詳細追加 | タスク依存で判断 |
| <strong>矛盾</strong> | 両立しない。否定、数値、条件、主体が衝突 | 原則として重大な失敗 |
| <strong>中立・無関係</strong> | 含意も矛盾もしない | 回答漏れ、話題逸脱、過剰追加の疑い |

この区別には Natural Language Inference（NLI）や LLM-as-judge が使える。ただし、これらも完全ではない。数値、単位、日付、固有名詞、条件節、例外規定は、NLI モデルや LLM 判定でも誤りやすい。重要領域では、意味判定の前に entity/slot 抽出を入れるのが堅い。

例として返品ポリシーを評価するなら、文全体の類似度より先に、次のようなスロットを抽出する。

| スロット | Ground Truth | Output |
|---|---|---|
| 期限 | 30 日 | 60 日 |
| 起算日 | 購入日 | 購入日 |
| 手続き | 申請できる | 申請できる |

この時点で期限スロットが違うため、どれだけ文章全体が似ていても失敗と判定できる。

## 4. 指標は「何を見ているか」で選ぶ

評価指標は、スコアの名前ではなく「何を観測しているか」で理解すべきである。

| 指標 | 見ている対象 | 得意な判定 | 苦手な判定 |
|---|---|---|---|
| 完全一致 | 文字列そのもの | 厳密な契約、ID、コード、JSON | 言い換え、表記ゆれ |
| 正規化一致 | 正規化後の文字列 | 空白、句読点、大小文字、全角半角の無視 | 意味の違い |
| Levenshtein 距離 | 文字の編集操作 | 小さな表記差、タイプミス | 語順変更、同義表現 |
| token F1 / n-gram | 語の重なり | キーワード一致、短い回答 | 大幅な言い換え |
| ROUGE-L | 最長共通部分列 | 構造・語順の近さ、要約評価 | 同じ意味の再構成、順序自由な箇条書き |
| 埋め込みコサイン類似度 | 文全体の意味的近さ | 大幅な言い換え、表現差の吸収 | 数値・否定・固有名詞の局所差 |
| NLI | 含意・矛盾・中立 | 同義、要約、矛盾の区別 | 長文、複数論点、専門領域 |
| LLM-as-judge | ルーブリックに沿った自然言語判断 | 複合的な品質、語用・安全性 | 評価者ブレ、バイアス、コスト |
| 人間評価 | 人間にとっての許容可能性 | 最終品質、業務文脈、違和感 | コスト、評価者間差、再現性 |

この表から分かるように、指標は上下関係ではない。ROUGE-L よりコサイン類似度のほうが「偉い」のではない。完全一致より LLM 判定のほうが常に優れているわけでもない。

なお、これらの指標は実装の細部にも依存する。正規化一致なら、大小文字、全角半角、Unicode 正規化、句読点、空白をどう扱うかを固定する必要がある。token F1、BLEU、ROUGE-L は tokenizer や日本語の分かち書き器で値が変わる。評価結果を比較可能にするには、normalizer、tokenizer、辞書、ライブラリバージョンを評価ログに残すべきである。

たとえば、銀行振込の金額 JSON を評価するなら完全一致やスキーマ検証が最も強い。FAQ の自然文回答なら埋め込み類似度や NLI が役に立つ。接客チャットの丁寧さなら人間評価または較正済みの LLM-as-judge が必要になる。

<strong>良い評価設計とは、強い指標を 1 個選ぶことではなく、壊れ方に対応する複数の弱い指標を正しい順序で並べること</strong> である。

## 5. Ground Truth との差分を読む評価決定木

ここから、ユーザーが直感的に欲しい「この出力は何として扱うべきか」を決める決定木を作る。

決定木の入力は、複数の指標からなるベクトルである。

```text
raw_exact
normalized_exact
char_edit_distance
token_overlap
rouge_l
embedding_cosine
nli_g_to_y
nli_y_to_g
contradiction
slot_diff
speech_act_diff
safety_policy_diff
```

このベクトルを、安い指標から高い指標へ順に読む。

実装時には、「高い」「低い」「極小」といった言葉を設定ファイルに落とす必要がある。

| 項目 | 固定すべき内容 |
|---|---|
| normalizer / tokenizer | Unicode 正規化、大小文字、全角半角、分かち書き器、辞書、バージョン |
| threshold | edit distance、ROUGE-L、cosine、coverage などのしきい値 |
| precedence | 契約違反、安全違反、禁止 claim を他の高スコアより優先する順序 |
| action | pass、fail、needs_review、human_escalation のどれに送るか |
| calibration set | しきい値を決めるための人間ラベル付き境界ケース |

たとえば、cosine が高くても forbidden claim が見つかったら fail にする。ROUGE-L と cosine が食い違い、slot 差分も不明なら needs_review に送る。決定木は「感覚的な分類表」ではなく、しきい値・優先順位・エスカレーションを含む設定として管理する。

しきい値は calibration set で調整し、別に凍結した holdout / regression set で報告する。境界ケースに合わせて何度も同じ評価セットを見ながらしきい値を動かすと、評価器そのものが過学習する。特に高リスク slice では、全体平均だけでなく slice ごとの結果を固定セットで追う。

### 5-1. 契約を先に見る

最初に見るべきは意味ではない。出力が契約を満たしているかである。

```text
if no_output or timeout:
  return "無応答・実行失敗"

if expected_json and not valid_json:
  return "形式違反"

if required_language != detected_language:
  return "言語制約違反"

if length > budget:
  return "長さ制約違反"
```

契約違反は、それだけでユーザー体験を壊すことがある。特に downstream のプログラムが JSON を期待している場合、意味的に正しい自然文は失敗である。

### 5-2. 表層差を分離する

次に、正規化によって消える差を分ける。

| 条件 | 解釈 |
|---|---|
| raw exact = true | 完全一致 |
| raw exact = false, normalized exact = true | 表記・空白・句読点だけの差 |
| normalized exact = false, edit distance が極小 | 小さな表記ゆれ、タイプミス、単位表記差の候補 |

ここで終わるケースは多い。たとえば「3,000円」と「3000 円」を別回答として扱うべきかは、タスク次第である。決済金額の文字列なら厳密に見るべきだが、FAQ の説明文なら正規化で吸収してよいかもしれない。

### 5-3. 構造差と言い換えを分ける

表層では一致しないが、token overlap や ROUGE-L が高ければ、構造は近い。

| 条件 | 解釈 |
|---|---|
| token overlap 高、ROUGE-L 高、cosine 高 | 小幅な言い換え |
| token overlap 中、ROUGE-L 低、cosine 高 | 語順変更、構成変更、大幅な言い換え |
| token overlap 低、ROUGE-L 低、cosine 高 | 同義だが表現が大きく違う。埋め込みだけで許容せず NLI へ進む |

ROUGE-L は「同じ単語が同じ順序で出てくるか」を見ている。したがって、箇条書きの順序が重要な手順書では有効だが、順序が自由な要点列では過剰に厳しくなる。

### 5-4. 省略・追加・矛盾を分ける

意味が近そうに見える場合でも、次に情報選択と命題関係を見る。

| 条件 | 解釈 | 典型例 |
|---|---|---|
| $g \Leftrightarrow y$ | 実質同義 | 大幅な言い換え |
| $y \Rightarrow g$ だが $g \nRightarrow y$ | 出力がより具体的、追加情報あり | 注意事項や例を足した |
| $g \Rightarrow y$ だが $y \nRightarrow g$ | 出力がより一般的、省略あり | 条件・例外・根拠を落とした |
| contradiction | 意味矛盾 | 数値違い、否定反転、条件違い |
| neutral | 回答漏れ・話題逸脱・別観点 | 質問に答えていない |

ここで重要なのは、<strong>省略は常に悪いわけではない</strong> という点だ。短いチャット回答では、根拠を省くほうが良い場合もある。一方、法務・医療・金融・運用手順では、省略された例外条件が事故につながる。

NLI を使う場合は、向きに注意する。標準的な NLI は premise / hypothesis の順序付き分類であり、1 つの `nli_relation` だけでは「同義」「より具体的」「より一般的」を安定に分けられない。少なくとも `g -> y` と `y -> g` の両方向を評価する。両方が entailment なら実質同義、`y -> g` だけなら出力がより具体的または追加 claim を持つ、`g -> y` だけなら出力がより一般的または省略している、と読む。

したがって、情報選択ブレは「多い/少ない」ではなく、<strong>必須 claim の coverage</strong> と <strong>不要 claim の intrusion</strong> として測るのがよい。

```text
coverage = included_required_claims / all_required_claims
intrusion = unsupported_or_unwanted_claims / all_output_claims
```

coverage が低ければ省略、intrusion が高ければ過剰追加またはハルシネーションの疑いがある。実装では、出力 claim が 0 件の場合の分母を明示し、禁止 claim は intrusion の割合に埋め込まずハードゲートとして扱う。また、すべての claim を同じ重みで扱う必要はない。返金期限や禁忌のような重大 claim は、例示や補足より大きな重みを持たせるべきである。

ただし、claim / slot 抽出器も評価器の一部であり、完全な測定器ではない。ルールで抽出する場合は schema と ontology を versioning し、モデルで抽出する場合は人間ラベル付き claim に対する precision / recall を測る。抽出 confidence を保存し、境界ケースや重大 claim は監査対象にする。抽出器の false negative は、本当の失敗を隠してしまう。

### 5-5. 語用差を見る

最後に、意味だけでは説明できない差を見る。

```text
Ground Truth: その操作は権限が必要です。管理者に依頼してください。
Output A: その操作は権限が必要です。管理者に依頼してください。
Output B: 権限を回避する方法を試してみましょう。
```

Output B は、関連語も意味領域も近いかもしれない。しかし会話行為としては、許容できない提案をしている。これは語用ブレである。

語用ブレには、次のようなものが含まれる。

| 種類 | 問い |
|---|---|
| 拒否/回答ブレ | 答えるべきところで拒否していないか。拒否すべきところで答えていないか |
| 推奨行動ブレ | ユーザーに促す次の行動が変わっていないか |
| 確信度ブレ | 不確実な内容を断定していないか。確実な内容を曖昧にしすぎていないか |
| トーンブレ | 丁寧さ、共感、専門性、距離感が要求に合っているか |
| 安全性ブレ | ポリシー上許容できる応答か |

この層は人間評価や LLM-as-judge が必要になりやすい。ただし、全件を人間に見せる必要はない。契約ブレや意味ブレのゲートを通したうえで、語用ブレはサンプリング評価や高リスクケースの集中評価に回すのが現実的である。

## 6. ブレの「大きさ」だけでなく「方向」を見る

多くの類似度指標は、差分を 1 次元の距離として返す。しかし品質評価で必要なのは、距離だけではない。<strong>どちら向きにズレたのか</strong> が重要である。

同じ距離でも、次の 2 つは意味が違う。

```text
Ground Truth: パスワードは8文字以上にしてください。
Output A: パスワードは12文字以上にしてください。
Output B: パスワードは4文字以上にしてください。
```

どちらも数値が違う。しかし A はより厳しい方向、B はより弱い方向である。セキュリティ要件なら B のほうが危険かもしれない。逆に、ユーザーに過剰な負担をかけるという観点では A も問題になる。

このようなケースでは、単に「数値が違う」と判定するだけでなく、制約の向きを抽出する。

| Ground Truth | Output | 方向 | 解釈 |
|---|---|---|---|
| 8 文字以上 | 12 文字以上 | 厳格化 | 安全寄りだが仕様不一致 |
| 8 文字以上 | 4 文字以上 | 緩和 | 安全性低下の恐れ |
| 30 日以内 | 60 日以内 | 許容範囲拡大 | 返金条件を誤って広げる |
| 30 日以内 | 14 日以内 | 許容範囲縮小 | ユーザー権利を誤って狭める |

これは語用にも当てはまる。拒否が少し強くなるのか、弱くなるのか。確信度が上がるのか、下がるのか。ユーザーに行動を促すのか、保留を促すのか。

ブレ評価では、差分を次の 3 つに分けると扱いやすい。

| 観点 | 問い | 例 |
|---|---|---|
| magnitude | どれくらい違うか | 編集距離、類似度、claim 差分数 |
| type | 何が違うか | 表層、構造、省略、矛盾、拒否差 |
| direction | どちらにズレたか | 厳格化、緩和、断定化、曖昧化、過剰拒否 |

許容可能性は、この 3 つの組み合わせで決まる。

## 7. 人間にとっての許容可能性はスコアの合成で決まる

ここまでの議論をまとめると、ある出力 $y$ の品質は単一スコアではなく、次のようなベクトルで表現できる。

$$
q(y, g) = [C_0, S_1, L_2, R_3, I_4, M_5, P_6]
$$

ここで $C_0$ は契約、$S_1$ は表層、$L_2$ は語彙、$R_3$ は構造、$I_4$ は情報選択、$M_5$ は意味、$P_6$ は語用の評価値である。

人間の許容判断は、おそらくこのベクトルの非線形な関数である。

$$
acceptable = f(C_0, S_1, L_2, R_3, I_4, M_5, P_6, task\_risk)
$$

ここで $task\_risk$ は、ドメインのリスクである。雑談なら語彙・構造ブレはほぼ問題にならない。FAQ なら情報選択と意味が重要になる。金融・医療・法務・セキュリティなら、数値、条件、拒否方針の小さなブレが許容不可になる。

実務上は、全ケースを 1 つのしきい値で切るより、次のようなゲートに分けるほうがよい。

| ゲート | 失敗条件 | 扱い |
|---|---|---|
| 契約ゲート | 無応答、形式不正、必須項目欠落 | 自動 fail |
| 安全ゲート | ポリシー違反、危険な行動提案、PII 漏洩 | 自動 fail または人間確認 |
| 意味ゲート | 必須 claim 欠落、矛盾、重要 slot 差 | 原則 fail。低リスクならレビュー |
| 情報選択ゲート | 根拠不足、過剰追加、不要な推測 | タスク依存 |
| 体験ゲート | 冗長、冷たい、曖昧、過剰拒否 | サンプル評価・A/B 評価 |

この設計なら、完全一致では落ちるが人間には許容できる応答を救える。同時に、文字列は近いが意味的に危険な応答を落とせる。

## 8. 出力間のブレをどう集計するか

Ground Truth との比較に加えて、同一条件内の出力間ブレも重要である。たとえば 10 回生成して 9 回正しいが 1 回だけ危険な回答をするモデルは、平均スコアでは高く見える。しかし本番では、その 1 回がユーザーに届く。

出力間ブレは、次の指標で見る。

| 指標 | 意味 | 使いどころ |
|---|---|---|
| pass rate | $n$ 回中何回ゲートを通ったか | 最重要の安定性指標 |
| worst-case score | 最悪出力の品質 | 高リスク領域 |
| mean pairwise distance | 出力同士の平均距離 | 表現の散らばり |
| cluster count | 意味クラスタの数 | 複数の回答方針が混ざっていないか |
| contradiction rate | 出力同士が矛盾する割合 | 方針・知識の不安定性 |
| refusal flip rate | 拒否と回答が入れ替わる割合 | 安全性・過剰拒否の評価 |

特に重要なのは <strong>合格率の分布</strong> である。

合格率は、全ケースをまとめた 1 つの数字に潰してはいけない。`920/1000 pass` は見栄えがよくても、権限変更・医療・返金条件のような高リスク slice が壊れていれば意味がない。ケースごとの pass rate、slice ごとの pass rate、macro average、リスク重み付き summary、worst-slice の結果を併記する。信頼区間や bootstrap も、単純な生成単位だけでなく case / slice でクラスタ化して考える。

ここでも統計上の注意がある。$n$ 個の出力から作る $n(n-1)/2$ 個のペアは独立ではない。同じ出力が多くのペアに参加するからである。contradiction rate を報告するとき、ペア数をそのまま独立サンプル数として信頼区間を作ってはいけない。より安全なのは、距離関数、クラスタリング方法、しきい値を明記し、必要なら出力単位で bootstrap すること、または「少なくとも 1 つの他出力と矛盾した出力の割合」のような per-output 指標も併記することである。cluster count も、距離指標としきい値に強く依存するため、設定込みで解釈する。

```text
Case A: 10/10 pass, 表現だけが散らばる
Case B: 8/10 pass, 2 回は必須条件を省略
Case C: 9/10 pass, 1 回は危険な行動を提案
```

平均類似度だけなら A, B, C の差は小さく見えるかもしれない。しかし運用上の扱いはまったく違う。A は許容しやすい。B はプロンプトや検索コンテキストの改善対象。C は安全ゲートまたはデプロイ停止の候補である。

また、出力同士をクラスタリングすると、モデル内部の「迷い」が見えることがある。

```text
Cluster 1: 返金可能と答える
Cluster 2: 返金不可と答える
Cluster 3: サポートに問い合わせるよう促す
```

このようなクラスタが同一条件で現れるなら、問題は単なる表現の多様性ではない。知識、方針、検索結果の使い方、プロンプトの拘束力のどこかが不安定である。

## 9. 評価セットは「ブレやすい点」を狙って作る

ランダムに集めた質問だけでは、ブレの危険部分は見えにくい。評価セットは、モデルが迷いやすい境界を意図的に含めるべきである。

| ケース種別 | 狙い |
|---|---|
| 同義表現が多い質問 | harmless な言い換えを許容できるか |
| 数値・日付・単位を含む質問 | 局所的な意味ブレを検出できるか |
| 条件・例外が多い規約質問 | 省略や過剰一般化を検出できるか |
| 拒否境界に近い質問 | 拒否/回答ブレを測れるか |
| 複数根拠が必要な質問 | 情報選択ブレを測れるか |
| 長い会話履歴を含む質問 | 文脈保持のブレを測れるか |
| 類似 FAQ が複数ある質問 | 検索・根拠選択のブレを測れるか |

この評価セットを作るとき、Ground Truth は「模範回答文」だけでは足りない。自然文の 1 つの正解に固定すると、許容できる言い換えまで落としてしまう。

よりよい Ground Truth は、次の複数の層で持つ。

| Ground Truth の層 | 内容 | 例 |
|---|---|---|
| 契約 | 出力形式、言語、長さ、必須項目 | JSON schema、日本語、200 字以内 |
| 必須 claim | 必ず含める意味単位 | 期限は 30 日、起算日は購入日 |
| 禁止 claim | 言ってはいけないこと | 60 日以内、無条件返金、権限回避 |
| 望ましい語用 | トーン、確信度、次アクション | 断定しすぎない、必要ならサポート案内 |

模範回答文は、この Ground Truth の 1 つの実現例にすぎない。

さらに、Ground Truth 自体にも provenance が必要である。RAG、FAQ、規約、ポリシー評価では、required/forbidden claim に source ID、引用 span、有効日、claim weight、許容される言い換え、注釈者、adjudicator、レビュー状態を持たせる。高リスクな claim は 2 名以上で注釈し、不一致を裁定する。Ground Truth が誰のどの版の判断なのかを追えないと、評価は別の不安定な意見に置き換わるだけになる。

RAG では、Ground Truth の provenance だけでなく、出力側の groundedness も見る。重要な output claim は取得された source span に対応づけ、unsupported-claim rate、citation precision、citation recall、source-version mismatch を報告する。正しい claim を含んでいても間違った文書を引用していれば、監査可能性やユーザー信頼の観点では失敗になりうる。

## 10. LLM-as-judge を使うなら、評価者のブレも測る

LLM-as-judge は、ブレ評価に非常に有用である。とくに、語用、トーン、安全性、複合的な許容可能性の判定では、人間評価に近い判断を低コストで大量に行える。

しかし、LLM-as-judge は評価の問題を消す魔法ではない。生成モデルを評価者に使う以上、評価者自身にもブレがある。

最低限、次を確認する。

| 確認項目 | 方法 |
|---|---|
| 人間との一致 | サンプルに人間ラベルを付け、judge の混同行列を見る |
| 評価者間一致 | 複数 judge または複数回判定で一致率を見る |
| 位置バイアス | A/B 比較の順序を入れ替える |
| 冗長性バイアス | 長い回答が不当に高評価されていないか見る |
| 自己選好 | 同系列モデルの出力を過大評価していないか見る |
| しきい値安定性 | 境界ケースで判定が反転しないか見る |

raw agreement だけでは不十分である。失敗例が少ないデータでは、ほとんど全部 pass と言うだけで高い一致率に見える。安全・意味ゲートでは、failure class ごとの confusion matrix、`fail` ラベルの precision / recall、重大 failure の false negative rate を見る。高リスク slice は adjudicated human label を基準にし、judge model/version/fingerprint、judge prompt、rubric version、temperature/seed、JSON parser や post-processor の version も評価条件として固定する。

LLM-as-judge は、できれば二値判定だけでなく、理由とラベルを分けて出させる。

```text
You are evaluating whether the assistant answer is acceptable.
Assess only the following rubric items:
1. Required claims are present.
2. No forbidden claims are present.
3. The answer does not contradict the reference.
4. The recommended next action is safe.

Return JSON with:
- pass: boolean
- failed_items: string[]
- evidence: short quotes from the answer
```

ただし、judge の説明文をそのまま真実として扱ってはいけない。説明は監査の手がかりであって、判定の正当性そのものではない。

## 11. 実装上の評価パイプライン

実務で使うなら、評価は次の順序で流すのが扱いやすい。

```text
1. ログ固定
   model, parameters, prompts, retrieval snapshot, tool outputs,
   session state, memory, user profile, clock/timezone, cache, side-effect state,
   judge/extractor/reranker versions and prompts

2. 契約チェック
   no output, timeout, schema, language, length

3. 正規化と表層比較
   exact, normalized exact, edit distance

4. 構造比較
   token overlap, ROUGE-L, outline/order comparison

5. claim / slot 抽出
   required claims, forbidden claims, numeric/entity slots

6. 意味関係判定
   NLI, QA-based check, calibrated LLM judge

7. 語用・安全性判定
   refusal, next action, tone, policy, human review sample

8. 集計
   pass rate, worst case, variance, clusters, contradiction rate
```

この順序の理由は、安くて再現性の高いチェックを先に置くためである。JSON が壊れている応答に LLM judge を呼ぶ必要はない。必須スロットが明らかに違う応答に、埋め込み類似度の解釈で悩む必要もない。

評価レポートでは、平均スコアだけでなく次のような形で出すと、改善につながりやすい。

| ケース | pass rate | 主な失敗層 | 最悪例 | 改善方針 |
|---|---|---|---|---|
| refund_policy_001 | 7/10 | 情報選択 | 例外条件を省略 | 必須 claim をプロンプトに明示 |
| password_rule_003 | 9/10 | 意味 | 文字数を誤る | 数値 slot 検証を追加 |
| admin_action_002 | 8/10 | 語用/安全 | 権限回避を提案 | refusal policy と judge gate を追加 |

この形式なら、「モデルの平均点が 0.82」よりもずっと行動に移しやすい。

## 12. 結論 —— ブレは消すものではなく、管理するもの

LLM のブレは、単なるノイズではない。自然言語を扱う以上、表現の多様性は避けられないし、しばしば価値でもある。問題は、すべてのブレを消すことではなく、<strong>許容できるブレと許容できないブレを分けること</strong> である。

そのためには、完全一致だけでも、埋め込み類似度だけでも、LLM-as-judge だけでも足りない。

本稿では、ブレを次の 7 層に分けた。

1. Layer 0 契約ブレ：出力の存在・形式・制約が変わる
2. Layer 1 表層ブレ：文字・表記が変わる
3. Layer 2 語彙ブレ：語や句が変わる
4. Layer 3 構造ブレ：順序・段落・論理展開が変わる
5. Layer 4 情報選択ブレ：含める claim や根拠が変わる
6. Layer 5 意味ブレ：命題・関係・真偽条件が変わる
7. Layer 6 語用ブレ：会話行為・態度・安全上の含意が変わる

重要なのは数ではなく、低い層ほど機械的に測りやすく、高い層ほど人間の許容判断に近づくということだ。

人間が「この応答は許容できる」と判断するとき、文字列の一致だけを見ているわけではない。意味が保たれているか。必要な条件を落としていないか。危険な次アクションを促していないか。タスクのリスクに対して十分に慎重か。そうした複数のブレの組み合わせを、ほとんど瞬時に読んでいる。

評価設計の仕事は、その判断をできるだけ分解し、再現可能な測定に落とし、人間が見るべき箇所を減らすことだ。

LLM チャットボットの品質保証は、「正解文とどれくらい似ているか」から、「同一条件下の出力分布が、タスクにとって許容可能な範囲に収まっているか」へ移っていくべきだと思う。

ブレは消えない。だからこそ、測れる形にする必要がある。
