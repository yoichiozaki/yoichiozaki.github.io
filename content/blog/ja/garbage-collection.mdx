C/C++ では、確保したメモリーを開発者が `malloc`/`free` で管理します。多くの現代的な言語では、不要になったメモリーを<strong>ガベージコレクター（GC）</strong>が自動で回収します。

GC の方式は、オブジェクトへの参照を数える参照カウントと、ルートから到達できるオブジェクトをたどるトレース方式に大きく分かれます。トレース方式には、断片化、停止時間、ヒープ全体の走査といった課題に対して、コンパクション、世代別 GC、並行 GC などの改良が重ねられてきました。各言語は、停止時間・スループット・メモリー使用量のどれを重視するかに応じて、これらの技術を組み合わせています。

## なぜ GC が必要なのか

手動メモリー管理には 2 つの典型的なバグがあります。

### メモリーリーク

使い終わったメモリーを解放し忘れると、プログラムのメモリー使用量が増え続け、最終的には OOM（Out of Memory）でクラッシュします。

```c
void leak_example() {
    char *buf = malloc(1024);
    // buf を使って処理...
    if (error) return;  // ← free(buf) を忘れてリターン！
    free(buf);
}
```

この例では、`error` が真の場合に `free` が呼ばれず、1024 バイトのメモリーがリークします。この関数が呼ばれるたびにリークが積み重なるため、長時間稼働するサーバーアプリケーションでは致命的な問題になります。

### ダングリングポインター

まだ使っているメモリーを誤って解放すると、その後のアクセスが解放済みメモリーへのアクセス（Use-After-Free）になります。

```c
void dangling_example() {
    char *a = malloc(64);
    char *b = a;  // a と b が同じメモリを指す
    free(a);
    // b はまだ解放済みメモリを指している（ダングリングポインタ）
    strcpy(b, "hello");  // 未定義動作！クラッシュやセキュリティ脆弱性の原因
}
```

GC は、プログラムから到達できなくなったオブジェクトだけを自動で回収します。開発者が解放のタイミングを指定しないので、解放忘れによるリークも、使用中のメモリーを解放してしまう Use-After-Free も起きません。

GC は 1959 年に John McCarthy が Lisp のために考案しました。その後、以下で紹介する多くのアルゴリズムが生まれ、改良されてきました。

## 参照カウント方式（Reference Counting）

各オブジェクトが「自分を何箇所から参照されているか」をカウンターとして持ちます。参照が増えるとカウントをインクリメントし、参照が外れるとデクリメントします。カウンターが 0 になった時点で、そのオブジェクトは即座に解放されます。

### 参照カウントの動作例

```python
a = Object()   # Object の ref_count = 1（a が参照）
b = a           # Object の ref_count = 2（a, b が参照）
a = None        # Object の ref_count = 1（b のみ参照）
b = None        # Object の ref_count = 0 → 即座に解放！
```

### 長所

- カウンターの増減だけで管理でき、実装がシンプルで理解しやすい
- ゴミは参照がなくなった時点で即座に回収されるので、レイテンシーを予測しやすい
- アプリケーション全体を停止させる Stop-The-World がない
- 不要になったオブジェクトがすぐに解放されるため、メモリーのピーク使用量が抑えられる

### 短所

- <strong>循環参照を回収できない</strong>: 最大の弱点。A→B→A のように互いを参照するオブジェクトは、外部から使われなくなっても回収されない

<CircularRefDiagram />

上図では、外部からの参照がなくなった後も、A と B の `ref_count` は互いからの参照で 1 のまま残ります。0 にならないので、2 つのオブジェクトは永久にリークします。

- ポインターの代入のたびにカウンターを更新するオーバーヘッドがある。特にマルチスレッド環境ではアトミック操作（`atomic_increment`/`atomic_decrement`）が必要で、キャッシュラインの競合が発生する
- 大きなデータ構造のルートの参照カウントが 0 になると、連鎖的に多数のオブジェクトの解放が走り（カスケード解放）、一時的なレイテンシースパイクになり得る

## トレース方式（Tracing GC）

トレース方式では、ルートの集合（スタック上の変数、グローバル変数、レジスターなど）からオブジェクトグラフを辿り、到達可能（reachable）なオブジェクトを「生きている」とマークします。到達不可能（unreachable）なオブジェクトはガベージとして回収されます。

### ルートセットとは

トレース GC における「ルート」とは、プログラムがほかのオブジェクトを経由せずに直接アクセスできるポインターのことで、次のものが含まれます。

- スタックフレーム上のローカル変数（各 goroutine / スレッドのスタック）
- グローバル変数（パッケージ / モジュールレベルの変数）
- CPU レジスター（現在のスレッドが保持しているポインター）

互いを参照し合うオブジェクトでも、ルートから辿れなければ回収されます。参照カウント方式では回収できない循環参照を扱えることが、トレース方式の大きな利点です。

## 三色マーク & スイープ（Tri-color Mark & Sweep）

三色マーク & スイープは、最も基本的で広く使われているトレース GC アルゴリズムです。Dijkstra らが 1978 年の論文 *"On-the-Fly Garbage Collection: An Exercise in Cooperation"* で提唱しました。

### 三色の意味

| 色 | 意味 | 状態 |
|---|---|---|
| 白 | まだ GC に発見されていない | 候補（ガベージかもしれない） |
| 灰色 | 発見されたが、参照先のスキャンがまだ完了していない | スキャン待ち |
| 黒 | 自身も参照先もすべてスキャン済み | 確実に到達可能（生存） |

### 三色不変条件（Tri-color Invariant）

アルゴリズムの正しさは、次の不変条件に依存します。

> 黒色オブジェクトが白色オブジェクトを直接参照することはない

GC は黒色のオブジェクトを再びスキャンしません。黒から白を直接参照していると、その白オブジェクトはスキャンの機会を失い、生きているのにゴミとして回収されてしまいます。白オブジェクトとの間に灰色オブジェクトがある限り、その灰色オブジェクトのスキャンを通じて白オブジェクトも必ず発見されます。

### アルゴリズムの流れ

1. すべてのオブジェクトを白色にする
2. GC ルートが指すオブジェクトを灰色にし、灰色スタック（ワークリスト）に追加する
3. 灰色スタックからオブジェクトを一つ取り出してスキャンする：
   - それが参照するオブジェクトのうち白色のものを灰色にし、灰色スタックに追加
   - 自身を黒色にする
4. 灰色スタックが空になるまで 3 を繰り返す（マーク完了）
5. ヒープを走査し、白色のまま残ったオブジェクトのメモリーを解放する（スイープ）

### Mark & Sweep の課題

基本的な Mark & Sweep には次の課題があります。

- <strong>フラグメンテーション</strong>: 解放されたオブジェクトの間に隙間ができ、メモリーが断片化する。大きなオブジェクトの割り当て時に連続領域が確保できないことがある
- <strong>Stop-The-World</strong>: マークとスイープの間、すべてのアプリケーションスレッドが停止する
- <strong>ヒープ全体の走査</strong>: スイープ時にヒープ全体を走査する必要があり、ヒープサイズに比例してコストが増大する

次節で扱う改良は、これらの課題に対応しています。断片化にはマーク & コンパクトとコピー GC、ヒープ全体の走査には世代別 GC、停止時間にはインクリメンタル GC と並行 GC が対処します。

## トレース GC の発展

### マーク & コンパクト（Mark-Compact）

Mark-Compact は、生存オブジェクトをヒープの一端に詰め直してメモリーの断片化（fragmentation）を解消します。

<FragmentationDiagram />

上図のように、スイープ後に生じた隙間をコンパクション（圧縮）で詰めると、ヒープ末尾に連続した空き領域ができます。

コンパクションの主なアルゴリズムは次のとおりです。

- <strong>Sliding compaction</strong>: オブジェクトをアドレス順にスライドさせる。オブジェクト同士の相対的な順序が保たれる
- <strong>Lisp 2 algorithm</strong>: ヒープを 3 回走査する。1 回目で新アドレスを計算、2 回目でポインターを更新、3 回目でオブジェクトを移動
- <strong>Threaded compaction</strong>: 参照をリンクリストに変換して一時情報を保存する。追加メモリー不要だが複雑

コンパクションはオブジェクトの移動と参照の書き換えを伴う重い処理ですが、空き領域が 1 か所にまとまるので、割り当てにバンプポインター（ポインターを進めるだけの方式）を使えます。バンプポインター割り当ては `alloc(size) = ptr; ptr += size` で済むため、空きブロックを探すフリーリスト方式より高速です。

### コピー GC（Copying / Semispace）

コピー GC は、ヒープを 2 つの領域（From 空間 / To 空間）に分割します。オブジェクトの割り当ては From 空間で行い、GC 時に生存オブジェクトを To 空間にコピーします。コピー後、From と To を交換し、古い From を一括で解放します。

代表的な実装は Cheney のアルゴリズム（1970 年）で、BFS（幅優先探索）でオブジェクトをコピーします。

```text
scan = free = To空間の先頭
GCルートから参照されるオブジェクトをTo空間にコピー, freeを進める
while scan < free:
    scanが指すオブジェクトの各フィールドについて:
        参照先がFrom空間にあり、まだforwardingされていなければ:
            To空間にコピーし、旧位置にforwarding pointerを設定し、freeを進める
        フィールドを参照先のTo空間アドレスに更新する
    scanを次のオブジェクトに進める
```

- <strong>長所</strong>: コピー先に詰めて配置するので別途コンパクションしなくても断片化しない、バンプポインターで高速に割り当てられる、ヒープ全体のスイープが不要
- <strong>短所</strong>: ヒープの半分しか使えない（メモリー効率が 50%）、大きなオブジェクトはコピーのコストが高い

### 世代別 GC（Generational GC）

世代別 GC は、次の<strong>弱い世代仮説（Weak Generational Hypothesis）</strong>に基づく最適化です。

> ほとんどのオブジェクトは生成直後に不要になる（若くして死ぬ）

この仮説は実際の観測に基づいています。典型的なアプリケーションでは、新規割り当てされたオブジェクトの 80〜95% が最初の GC までに不要になります。

<GenerationalHeapDiagram />

- <strong>Young 世代（新世代）</strong>: 新規オブジェクトを割り当てる小さな領域。Minor GC が頻繁に走りますが、ほとんどのオブジェクトが死んでいるため数ミリ秒で終わります。Eden 領域で新規割り当てを行い、Minor GC で生存したオブジェクトは Survivor 空間にコピーされます
- <strong>Old 世代（旧世代）</strong>: 何度も Minor GC を生き延びたオブジェクトが昇格（promotion）する領域。GC の頻度は低いが、処理は重い（Major GC / Full GC で数十〜数百ミリ秒）

Minor GC では Young 世代だけを調べますが、Old 世代から Young 世代への参照も生存の根拠として扱う必要があります。この参照を Old 世代全体をスキャンせずに見つけるために、世代別 GC はリメンバードセット（Remembered Set）で世代間の参照を記録します。実装にはカードテーブル方式が一般的です。Old 世代のメモリーを 512 バイト程度のカード単位に分割し、Young 世代への参照を含むカードだけを「ダーティー」とマークしてスキャン対象にします。

### インクリメンタル GC / 並行 GC

インクリメンタル GC と並行 GC は、GC 処理をアプリケーションの実行と交互に、または同時に進めて、Stop-The-World（STW）の時間を短くします。

<ConcurrencyTimeline />

- <strong>Stop-The-World GC</strong>: マーク＋スイープの間、アプリケーションを完全に停止。実装は最もシンプルだが、停止時間が長い（ヒープサイズに比例）
- <strong>インクリメンタル GC</strong>: マーク処理を小さなステップに分割し、アプリケーションの実行と交互に進めます。各ステップの停止は短いが、合計の GC 時間は長くなる（書き込みバリアのオーバーヘッド）
- <strong>並行 GC（Concurrent GC）</strong>: マーク処理を別スレッドで並行実行。アプリケーションが停止するのはマーク開始時と最後の再マーク時だけで、どちらも極めて短い

並行 GC では、アプリケーション（ミューテーター）と GC（コレクター）が同時に動くため、マーク中にオブジェクトの参照関係が変わることがあります。これに対処するのが書き込みバリア（Write Barrier）です。

## 書き込みバリア（Write Barrier）

書き込みバリアは、並行 GC やインクリメンタル GC で三色不変条件を維持するための仕組みです。ミューテーターがポインターを書き換える箇所に、変更を GC に伝えるコードが挿入されます。

### なぜ書き込みバリアが必要か

次の順に処理が進む場合を考えます。

```text
1. GC がオブジェクト A を黒色にスキャン済み
2. アプリケーションが A.field = C（白色）を実行
3. アプリケーションが B.field = nil（B→C の参照を削除。B は灰色/白色）
4. GC は B をスキャンするが、もう C への参照がない
5. C は白色のまま → ガベージとして解放される → 生きているのに解放！
```

この問題を<strong>ロストオブジェクト問題</strong>と呼びます。黒→白の参照が作られ（条件①）、かつその白オブジェクトへの他の経路がすべて切断された（条件②）場合に発生します。

### 主要な書き込みバリア

<strong>① Dijkstra バリア（挿入バリア）</strong>

ポインターに新しい参照先を書き込むときに、その参照先を灰色にします。

```text
// A.field = C を実行する際に挿入されるバリア
writeBarrier(A, field, C):
    shade(C)      // まず C を灰色にする（黒→白の参照を防ぐ）
    A.field = C   // その後にストアを実行
```

shade はストアの<strong>前に</strong>実行します。順序が逆だと、ストアと shade の間に「黒オブジェクト A が白オブジェクト C を参照している」状態が生まれ、並行して動く GC がその瞬間に C をガベージと判断するおそれがあります。

新しく参照されたオブジェクトは必ず灰色になるので、確実にスキャンされます。ただし、保守的に多くのオブジェクトを灰色にするため、浮遊ガベージ（本当はゴミだが今回は回収されない）が増える傾向があります。

<strong>② Yuasa バリア（削除バリア / snapshot-at-the-beginning）</strong>

参照が外される側のオブジェクト（上書きされる古い参照先）を灰色にします。GC 開始時点のオブジェクトグラフを「スナップショット」として保つ考え方です。

```text
// A.field が old → new に変わる前に挿入されるバリア
writeBarrier(A, field, new):
    old = A.field
    if old is white:
        shade(old)  // old を灰色にする
    A.field = new
```

これにより、GC 開始時に到達可能だったオブジェクトはすべてマークされます。

<strong>③ ハイブリッドバリア（Go 1.8+）</strong>

Go は Dijkstra バリアと Yuasa バリアを組み合わせたハイブリッド書き込みバリアを採用しています。

```text
writeBarrier(slot, new):
    shade(*slot)  // 削除バリア: 上書きされる古い値を灰色にする
    if current stack is gray:
        shade(new) // 現在のスタックがまだスキャン対象の間だけ挿入バリア
    *slot = new
```

この擬似コードは Go の `mbarrier.go` のコメントに沿っています。削除バリアは上書きされる古い値を常に shade しますが、挿入バリアで新しいポインターを shade するのは、現在の goroutine のスタックが灰色の間だけです。スタックが黒になれば `shade(new)` は不要になります。

ハイブリッド方式の最大の利点は、<strong>スタックの再スキャンが不要</strong>になることです。Dijkstra バリアだけを使っていた Go 1.5〜1.7 では、マーク終了時にすべての goroutine のスタックを再スキャンする必要があり、これが STW 時間の大きな原因でした。ハイブリッドバリアにより、Go の STW 停止は典型的にはサブミリ秒、ワークロードやプラットフォームによってはさらに短く抑えられます。

## メモリーアロケーション戦略

GC のアルゴリズムによって、使える割り当て方式が変わります。オブジェクトを移動しない GC では空きブロックを探すフリーリストを使い、コンパクションやコピーで空き領域をまとめる GC ではバンプポインターを使えます。

### フリーリスト（Free List）

フリーリスト方式は、解放されたメモリーブロックをリンクリストで管理し、割り当て時に要求サイズに合うブロックを探します。探し方には次の種類があります。

- <strong>First-fit</strong>: 最初に見つかった十分なサイズのブロックを使う
- <strong>Best-fit</strong>: 最もサイズが近いブロックを使う（断片化が少ない）
- <strong>Segregated-fit</strong>: サイズクラスごとに別のリストを持つ（Go, tcmalloc が採用）

### バンプポインター（Bump Pointer）

バンプポインターは、コンパクション済みのヒープやコピー GC で使われる方式です。空きメモリーの先頭にポインターを置き、割り当てのたびにポインターを進めるだけです。

```text
alloc(size):
    result = freePtr
    freePtr += size
    return result
```

極めて高速（実質 1 命令）ですが、連続した空き領域が必要です。

### スレッドローカル / プロセッサーローカルな割り当てバッファー

実行コンテキストごとにヒープの一部を事前に確保し、マルチスレッド環境での割り当て競合を避ける仕組みです。Java HotSpot は TLAB（Thread-Local Allocation Buffer）を使い、各 Java スレッドがロックなしのバンプポインターで割り当てます。Go のアロケーターはこれとは別の設計で、TLAB の代わりに P ごとの `mcache` とサイズクラス別の span を使います。

## 言語ごとの GC 戦略

### Go — 並行三色マーク & スイープ

Go の GC は、シンプルさとレイテンシーの低さを最優先にした設計です。

| 項目 | 内容 |
|---|---|
| アルゴリズム | 並行三色マーク & スイープ |
| 世代別 | なし（非世代別） |
| コンパクション | なし |
| STW | マーク開始・終了時のみ（典型的にはサブミリ秒。ワークロード依存） |
| 書き込みバリア | ハイブリッド（Dijkstra + Yuasa） |
| チューニング | `GOGC` / `GOMEMLIMIT` |

<strong>なぜ Go は世代別 GC ではないのか？</strong>Go のコンパイラーはエスケープ解析（escape analysis）を行い、関数外に参照が漏れないオブジェクトをスタックに割り当てます。そのため短命なオブジェクトの多くはヒープに到達せず、世代別 GC の前提（「多くのヒープオブジェクトが短命」）が弱くなります。世代別にしても得られる効果が小さく、書き込みバリアのコストに見合いません。

<strong>GC ペーサー</strong>: 次の GC サイクルをいつ開始するかは「ペーサー」が決めます。`GOGC=100`（デフォルト）では、前回の GC 後のライブヒープサイズに対してヒープが 100% 成長した時点で次の GC を開始します。Go 1.19 で追加された `GOMEMLIMIT` では、メモリー制約のある環境で OOM を防ぐために、メモリー使用量の上限をソフトリミットとして設定できます。

<strong>Green Tea GC（Go 1.26 で既定化）</strong>: 従来の Go のマーカーはオブジェクト単位でポインターをたどるため、小さなオブジェクトが大量にあるとメモリーアクセスがランダムになり、キャッシュ効率が落ちます。[Green Tea GC](https://go.dev/doc/go1.26#new-garbage-collector) はマーク対象をスパン（同じサイズクラスのページ）単位でまとめて処理し、局所性と CPU スケーラビリティーを改善しました。Go 1.25 で実験的に導入され、Go 1.26 で既定有効になっています。公式リリースノートによると、GC を多用する実プログラムで GC オーバーヘッドが 10〜40% 削減され、Ice Lake / Zen 4 以降の amd64 ではベクター命令を使ってさらに約 10% の改善が見込まれます。アルゴリズムの骨格（並行三色マーク & スイープ、非世代別、非コンパクション）は変わっておらず、変わったのはマーク時にメモリーをどう走査するかという実装の部分です。

GC のソースコードは [`runtime/mgc.go`](https://github.com/golang/go/blob/master/src/runtime/mgc.go) にあります。

### Java (HotSpot) — 世代別 + 多彩なコレクター

Java（HotSpot）には、用途に応じて選べる複数のコレクターがあります。

| コレクター | 特徴 | STW | ユースケース |
|---|---|---|---|
| Serial GC | シングルスレッド | 長い | 小規模アプリ、クライアント |
| Parallel GC | マルチスレッドマーク | 中程度 | スループット重視のバッチ処理 |
| G1 GC | リージョンベース、予測可能な停止 | 短い（目標指定可） | 汎用（JDK 9+ デフォルト） |
| ZGC | 着色ポインター、TB級ヒープ | < 1ms | 低レイテンシー要求 |
| Shenandoah | 並行コンパクション | < 10ms | 低レイテンシー（Red Hat が開発） |

<strong>G1 GC の仕組み</strong>: ヒープを均等なリージョン（通常 1〜32MB）に分割します。Young/Old の区別はリージョン単位で動的に割り当てられます。G1 は「ガベージの多いリージョン」を優先的に回収（Garbage-First）し、限られた停止時間内で回収できるメモリーを最大にします。`-XX:MaxGCPauseMillis=200` のように停止時間の目標を設定できます。

<strong>ZGC の着色ポインター（Colored Pointers）</strong>: ZGC はオブジェクトポインターの未使用ビットに GC のメタデータ（マーク状態、リロケーション状態）を埋め込むので、オブジェクトヘッダーにマーク情報を書き込む必要がありません。非世代別 ZGC は着色ポインターとロードバリアで並行マーク / リロケーションを実現し、世代別 ZGC はさらに世代間参照を追跡するストアバリアも使います。これらの技術により、ZGC は TB 級のヒープでも STW を 1ms 以下に抑えます。

### Python (CPython) — 参照カウント + 世代別トレース GC

CPython は、参照カウントとトレース GC を組み合わせたハイブリッド方式です。

<PythonHybridDiagram />

- <strong>参照カウント（Primary）</strong>: メインのメモリー回収方式。オブジェクトの `ob_refcnt` が 0 になると即座に `tp_dealloc` が呼ばれて解放される
- <strong>世代別トレース GC（Auxiliary）</strong>: 参照カウントでは回収できない循環参照を検出・回収するために、割り当て数に応じて世代別のトレース GC を定期的に実行

<strong>3 世代の閾値システム</strong>:

| 世代 | 閾値（デフォルト） | 意味 |
|---|---|---|
| Generation 0 | 2000（3.12 以前は 700） | 割り当て数 − 解放数 が閾値を超えたら Gen 0 コレクションを実行 |
| Generation 1 | 10 | Gen 0 コレクションが 10 回走るたびに Gen 1 コレクションも実行 |
| Generation 2 | 10 | Gen 1 コレクションが 10 回走るたびに Gen 2 コレクションも実行 |

閾値が決めるのは各世代をコレクションする頻度で、昇格に必要な生存回数ではありません。オブジェクトは Gen N のコレクションを 1 回生き延びるだけで Gen N+1 に昇格します。閾値は `gc.get_threshold()` で確認でき、`gc.set_threshold()` で変更できます。

CPython では GIL（Global Interpreter Lock）があるため、参照カウントの更新にアトミック操作は不要です。GIL を持たない free-threaded ビルド（`--disable-gil`）では、バイアス参照カウント（biased reference counting）を使います。オブジェクトを所有するスレッドは通常のインクリメント/デクリメントでカウンターを更新し、他のスレッドだけがアトミック操作を使うことで、GIL なしでもスレッドセーフな参照カウントを実現します。free-threaded ビルドは Python 3.13 で実験的に導入され、[PEP 779](https://peps.python.org/pep-0779/) により Python 3.14 で正式サポート（ただし依然としてオプションのビルド）となりました。

<strong>3.14 で導入され、撤回されたインクリメンタル GC</strong>: CPython 3.14.0〜3.14.4 は、大きなヒープでの最大停止時間を桁違いに短縮することを狙って、世代を young / old の 2 つに絞ったインクリメンタル GC を採用していました。しかし本番環境でメモリー圧迫の報告が相次いだため、[3.14.5 で 3.13 相当の世代別 GC に巻き戻されました](https://docs.python.org/3/whatsnew/3.14.html#notable-changes-in-3-14-5)。上で説明した 3 世代方式は、この巻き戻し後の GC です。この事例が示すように、GC の設計ではベンチマーク上の停止時間の短さと、実際のワークロードでのピークメモリー使用量とを比べて判断する必要があります。

### JavaScript (V8) — 世代別 + 並行マーク

V8 エンジン（Chrome, Node.js, Deno）は世代別 GC を採用しています。

| 領域 | 名称 | アルゴリズム |
|---|---|---|
| Young 世代 | Nursery (Scavenger) | Semispace コピー GC |
| Old 世代 | Major GC | 並行マーク & スイープ/コンパクト |

<strong>Scavenger の仕組み</strong>: Young 世代は 2 つの semispace に分けられます。新規オブジェクトは「From」空間に割り当てられ、Minor GC（Scavenge）時に生存オブジェクトが「To」空間にコピーされます。2 回生存したオブジェクトは Old 世代に昇格します。

<strong>Orinoco</strong>: V8 の GC 最適化プロジェクトの名前です。メインスレッドと並行・並列に GC 処理を進め、STW 時間を短くしています。主な手法は次のとおりです。

- <strong>Concurrent Marking</strong>: ワーカースレッドがメインスレッドと並行してオブジェクトグラフを走査
- <strong>Parallel Scavenging</strong>: 複数のワーカースレッドが Young 世代の GC を並列実行
- <strong>Incremental Marking</strong>: マーク処理を細切れに進め、アイドル時間やタスク間の短い隙間で実行
- <strong>Lazy Sweeping</strong>: スイープ処理をオブジェクトの割り当て時に遅延実行

### .NET (CLR) — 世代別マーク & コンパクト

.NET の GC には、クライアントアプリ向けの Workstation GC と、サーバーワークロード向けの Server GC の 2 つのモードがあります。

| 項目 | 内容 |
|---|---|
| アルゴリズム | 世代別マーク & コンパクト |
| 世代数 | 3（Gen 0, 1, 2）+ LOH (Large Object Heap) |
| モード | Workstation GC / Server GC |
| 並行 | Background GC（Gen 2 の並行コレクション） |

<strong>Large Object Heap (LOH)</strong>: 85,000 バイト以上のオブジェクトは LOH に直接割り当てられます。LOH はデフォルトではコンパクションされませんが、.NET Framework 4.5.1 以降では `GCSettings.LargeObjectHeapCompactionMode` で明示的にコンパクションを要求できます。

<strong>ピン留め（Pinning）</strong>: ネイティブコードとの相互運用時に、GC がオブジェクトを移動することを防ぎます。`fixed` ステートメントや `GCHandle.Alloc(obj, GCHandleType.Pinned)` で実現しますが、多用するとフラグメンテーションの原因になります。

### Rust — GC なし（所有権システム）

Rust は GC に頼らず、所有権（ownership）、借用（borrowing）、ライフタイムのコンパイル時チェックでメモリー安全を保証します。

```text
所有権システム → コンパイル時にメモリ解放のタイミングが決定
             → GC ランタイムがなく、GC による停止も起きない
```

RAII（Resource Acquisition Is Initialization）パターンにより、変数がスコープを抜けると自動的に `Drop` トレイトが呼ばれてリソースが解放されます。呼び出し位置はコンパイル時に決まりますが、デストラクターや解放処理そのものは実行時に走ります。Rust が避けているのは、トレース GC のランタイムと GC 停止です。

循環参照が必要な場合は `Rc<T>` / `Arc<T>` + `Weak<T>` を使い、参照カウントで管理します。`Weak<T>` は所有権を持たない参照で、`Rc` の強参照カウントに数えられないため、循環の一部を `Weak<T>` にすれば循環を断ち切れます。

### Swift — ARC（Automatic Reference Counting）

Swift はコンパイル時に参照カウントの増減コードを自動挿入する ARC を採用しています。

- ランタイムでのトレース GC は不要
- コンパイル時にすべての retain/release が挿入されるため、実行時のオーバーヘッドが予測しやすい
- 循環参照は `weak`（Optional になる）/ `unowned`（非 Optional、ライフサイクルが保証される場合）参照で開発者が明示的に解決する必要がある

Swift のコンパイラーは ARC 最適化として、不要な retain/release のペアを除去するパス（Copy-on-Write 最適化を含む）を持っています。

## まとめ

| 言語 | GC 方式 | 世代別 | 並行 | STW | 割り当て方式 |
|---|---|---|---|---|---|
| Go | 三色 M&S | No | Yes | sub-ms typical | Segregated-fit |
| Java | 選択可（G1/ZGC/Shenandoah） | Yes | Yes | < 1ms〜 | TLAB + バンプポインター |
| Python | 参照カウント + トレース | Yes (3世代) | No | あり | pymalloc arena |
| JavaScript (V8) | コピー + M&S/Compact | Yes | Yes | 短い | Semispace + Free list |
| .NET | 世代別 M&C | Yes (3世代+LOH) | Yes | 短い | バンプポインター |
| Rust | なし（所有権） | — | — | なし | システムアロケーター |
| Swift | ARC | — | — | なし | ARC + malloc |

GC の方式は、言語ランタイムの停止時間、スループット、メモリー使用量を左右する設計判断です。参照カウントは単純で即座に回収できますが循環参照を扱えず、トレース GC は循環参照も回収できる代わりに停止やヒープ走査のコストを伴います。世代別 GC は短命なオブジェクトが多いという仮説を使ってこのコストを減らし、並行 GC は書き込みバリアのオーバーヘッドと引き換えに停止時間を短くします。上の表の違いは、各言語がワークロードと要件に合わせて、これらのトレードオフからどれを選んだかの違いです。
