## はじめに

Google 検索、IDE のコード検索、EC サイトの商品検索は、大量のドキュメントの中からクエリーに合うものを短時間で探して並べる。どれも検索エンジンの同じ基本技術の上に成り立っている。

その中心となるのは次の 3 つの技術で、この記事ではそれぞれをインタラクティブな図解で説明する。

1. **転置インデックス** — 単語から、それを含むドキュメントを引くデータ構造
2. **ブーリアン検索** — クエリーを集合演算で処理する仕組み
3. **TF-IDF / BM25** — 検索結果に順位を付けるスコア計算

## テキスト解析 — ドキュメントをトークンに分解する

検索エンジンは、ドキュメントを受け取るとまずテキスト解析で生のテキストを検索可能な単位（**トークン**）に変換する。

<TokenizationDiagram />

このパイプラインは次の 4 つの処理からなる。

### 1. 文字正規化

Unicode 正規化や、大文字から小文字への変換を行う。これで `"The"` と `"the"` が同じトークンになる。

### 2. トークナイゼーション

テキストを個々の単語（トークン）に分割する。英語では空白で区切るのが基本だが、日本語のように単語間にスペースがない言語では、MeCab や Kuromoji による形態素解析などで区切る必要がある。

### 3. ストップワード除去

`"the"`、`"is"`、`"on"` のように出現頻度が高く、ドキュメントを区別する情報の少ない単語を除去する。インデックスが小さくなり、検索精度も上げられる。

### 4. ステミング / レンマタイゼーション

`"running"` → `"run"`、`"cats"` → `"cat"` のように、単語を原形に戻す。語形が違っても同じ語として一致するので、検索のリコール（再現率）が上がる。

## 転置インデックス — 単語からドキュメントを引く

### なぜ転置インデックスが必要か

素朴に全文検索を実装すると、各ドキュメントを先頭から走査してキーワードを探すことになる。$N$ 個のドキュメントに対して計算量は $O(N \times L)$（$L$ は平均ドキュメント長）で、ドキュメント数が増えると実用的な時間で答えられなくなる。

転置インデックス（Inverted Index）を使うと、この全件走査が不要になる。

### Forward Index vs Inverted Index

Forward Index は「ドキュメント → 含まれる単語」という対応を持つ。

```text
Forward Index:
  D1 → [cat, sat, mat]
  D2 → [cat, dog]
  D3 → [dog, sat, log]
```

転置インデックスはこの対応を逆向きにし、「単語 → その単語を含むドキュメント」を持つ。

```text
Inverted Index:
  cat → [D1, D2]
  dog → [D2, D3]
  log → [D3]
  mat → [D1]
  sat → [D1, D3]
```

インデックスに登録された各単語（ターム）に紐づくドキュメント ID のリストを**ポスティングリスト**（Posting List）と呼ぶ。ハッシュベースのターム辞書なら、あるキーワードのポスティングリストを期待 $O(1)$ で見つけられる（$T$ 個のタームを持つ木/FST 型の辞書では $O(\log T)$）。実際のクエリー時間の大半は、見つけたポスティングリストの読み出しと結合にかかる。

### ポスティングリストの構造

実際の検索エンジンでは、ポスティングリストにドキュメント ID 以外の情報も持たせることが多い。

| フィールド | 用途 |
|-----------|------|
| ドキュメント ID | 基本的なドキュメント識別 |
| 出現頻度（TF） | ランキングに使用 |
| 出現位置 | フレーズ検索、近接検索 |
| オフセット | スニペット生成、ハイライト |

位置情報を含むインデックスを**ポジショナルインデックス**と呼ぶ。単語の位置が分かるので、`"cat sat"` のようなフレーズ検索ができる。

## クエリー処理 — ブーリアン検索モデル

クエリーをドキュメントと同じ手順でトークン化したら、転置インデックスで該当するドキュメントを探す。最も基本的なモデルがブーリアン検索だ。

<BooleanQueryDiagram />

### AND（積集合）

`"cat AND sat"` は、`cat` と `sat` のポスティングリストの積集合（intersection）を求める。どちらのリストもドキュメント ID でソート済みなので、2 つのポインターで両リストを先頭からたどるマージにより、$O(n + m)$（$n$、$m$ は各リストの長さ）で処理できる。

```python
def intersect(p1, p2):
    result = []
    i, j = 0, 0
    while i < len(p1) and j < len(p2):
        if p1[i] == p2[j]:
            result.append(p1[i])
            i += 1
            j += 1
        elif p1[i] < p2[j]:
            i += 1
        else:
            j += 1
    return result
```

### OR（和集合）

`"cat OR sat"` は両方のポスティングリストの和集合で、いずれかのタームを含む全ドキュメントを返す。

### クエリー最適化

AND 条件が複数ある場合は、ポスティングリストが最も短いタームから処理すると中間結果が小さく保たれ、処理が速くなる。

## ランキング — TF-IDF と BM25

ブーリアン検索が返すのは「一致する / しない」の二値だけだ。実際の検索では、どのドキュメントがクエリーに最も関連するかで順位を付けたい。そのためのスコアが TF-IDF と BM25 だ。

<TFIDFDiagram />

### TF: 出現頻度（Term Frequency）

$$
\text{TF}(t, d) = \text{ドキュメント } d \text{ 中のターム } t \text{ の出現回数}
$$

あるタームがドキュメント内で多く出現するほど、そのドキュメントはそのタームに関連する可能性が高い。

### IDF: 逆文書頻度（Inverse Document Frequency）

$$
\text{IDF}(t) = \log_{10}\!\left(\frac{N}{\text{df}(t)}\right)
$$

$N$ は全ドキュメント数、$\text{df}(t)$ はターム $t$ を含むドキュメント数。`"the"` のようにどこにでも出現する単語は IDF が低く、`"algorithm"` のように一部のドキュメントにしか出現しない単語は IDF が高い。少数のドキュメントにしか出てこない単語ほど、ドキュメントを区別する手がかりになる。IDF はこれを数式で表している。

### TF-IDF スコア

$$
\text{TF-IDF}(t, d) = \text{TF}(t, d) \times \text{IDF}(t)
$$

クエリーに複数タームがある場合、各タームの TF-IDF を合算してドキュメントの最終スコアとする。

### BM25: TF-IDF の改良

TF-IDF には弱点がある。例えば、あるタームが 100 回出現するドキュメントは 1 回のドキュメントの 100 倍のスコアになるが、関連度にそこまでの差があるとは限らない。

**BM25**（Best Matching 25）は TF-IDF を改良したスコアで、多くの検索エンジンで使われている（Lucene では 6.0 以降のデフォルト）。

$$
\text{IDF}_{\text{BM25}}(t) = \log\!\left(1 + \frac{N - \text{df}(t) + 0.5}{\text{df}(t) + 0.5}\right)
$$

$$
\text{BM25}(t, d) = \text{IDF}_{\text{BM25}}(t) \cdot \frac{\text{TF}(t,d) \cdot (k_1 + 1)}{\text{TF}(t,d) + k_1 \cdot \left(1 - b + b \cdot \frac{|d|}{\text{avgdl}}\right)}
$$

パラメーターは 2 つある。$|d|$ はドキュメント $d$ の長さ（ターム数）、$\text{avgdl}$ は全ドキュメントの平均の長さだ。

- **$k_1$**（一般に 1.2〜2.0、Lucene のデフォルトは 1.2）: TF の飽和を制御する。$K = k_1 \cdot \left(1 - b + b \cdot \frac{|d|}{\text{avgdl}}\right)$ とおくと、TF が増えても TF 飽和因子 $\frac{\text{TF} \cdot (k_1+1)}{\text{TF}+K}$ は $(k_1 + 1)$ に漸近し、際限なく増加しない
- **$b$**（一般に 0.75）: ドキュメント長の正規化。長いドキュメントは単語数が多いぶん TF が高くなりやすいので、$b$ でこの偏りを補正する

## 実践的な話題

### インデックス圧縮

ポスティングリストはドキュメント ID のソート済み整数列なので、差分符号化（delta encoding）と可変長バイト符号（Variable Byte Encoding）を組み合わせて効率的に圧縮できる。

```text
元のリスト:  [101, 105, 108, 120]
差分符号化:    [101,   4,   3,  12]  ← 小さな数値になる
可変長バイト:  バイト列に効率的にパック
```

### 分散検索

大規模な検索エンジンでは、インデックスを複数のノードにシャーディング（分割配置）する。クエリーは全シャードに配信され（scatter）、各シャードの結果を集約（gather）して最終ランキングを作る。Elasticsearch などもこの scatter-gather 方式を使っている。

### Apache Lucene と Elasticsearch

[Apache Lucene](https://lucene.apache.org/) は Java で書かれた転置インデックスベースの全文検索ライブラリーで、この分野の事実上の標準だ。内部では次のような最適化が行われている。

- **セグメント化**: インデックスを不変のセグメントに分割し、書き込みと読み取りを並行して進められるようにする
- **スキップリスト**: ポスティングリスト内を飛ばし読みして、積集合の計算などを速くする
- **ブロック符号化**: ポスティングリストをブロック単位で符号化し、SIMD で高速に処理する

[Elasticsearch](https://www.elastic.co/elasticsearch) は Lucene 上に構築された分散検索エンジンで、REST API、クラスタリング、ほぼリアルタイムのインデキシングを提供する。

## まとめ

転置インデックスは「ターム → ポスティングリスト」の対応を持ち、ターム辞書の引き当てはハッシュなら期待 $O(1)$、木/FST なら $O(\log T)$ で済む。ブーリアン検索は、ソート済みのポスティングリスト同士の集合演算でクエリーを処理する。TF-IDF と BM25 は、タームの出現頻度と、そのタームを含むドキュメントの少なさを組み合わせて関連度を計算し、結果に順位を付ける。

検索ボックスにキーワードを入れてすぐに結果が返ってくる裏では、こうした転置インデックスの参照とスコア計算が行われている。
