## async/awaitは何を隠しているのか

JavaScript、Python、Rust、C# など多くの言語が、非同期処理を書くための構文として `async/await` を採用しています。構文は似ていても、その裏側で動く仕組みは言語やランタイムによって大きく異なります。

```javascript
async function fetchData() {
  const response = await fetch("/api/data");
  const json = await response.json();
  return json;
}
```

このコードを実行するとき、ランタイムは次の処理をしています。

1. `await` で関数の実行を<strong>中断（suspend）</strong>し、制御をランタイムに返す
2. I/O の完了をスレッドを止めずに監視する
3. I/O が完了したら、中断した位置から関数の実行を<strong>再開（resume）</strong>する
4. その間、ほかの非同期処理をスケジューリングして実行する

以下では、JavaScript のイベントループ、Python の asyncio、Rust のポーリングベースの Future という3つの実行モデルを順に見ます。

## 前提知識：同期・非同期・並行・並列

この4つの用語は混同されやすいので、先に意味を確認しておきます。

| 用語 | 意味 |
|------|------|
| 同期（Synchronous） | 処理が完了するまでブロックして待つ |
| 非同期（Asynchronous） | 処理を開始したら完了を待たずに次に進み、完了時に通知を受ける |
| 並行（Concurrent） | 複数のタスクの実行期間が重なっている（シングルコアでも可能） |
| 並列（Parallel） | 複数のタスクが物理的に同時に実行されている（マルチコアが必須） |

async/awaitは<strong>並行性（concurrency）</strong>を実現する仕組みで、並列に実行されるとは限りません。例えば JavaScript の async/await は、1つのスレッドの上で複数の処理を並行に進めます。

## JavaScript：イベントループモデル

### イベントループの構造

JavaScriptのコードはシングルスレッドで実行されます。1つのスレッドで複数の非同期処理を扱うために使われるのが<strong>イベントループ</strong>です。

イベントループの動作には、次の4つの要素が関わります。

1. <strong>コールスタック</strong> — 現在実行中の関数のスタック
2. <strong>Web API / Node API</strong> — タイマー、ネットワーク、ファイルI/Oなどの非同期操作を実行する環境
3. <strong>マイクロタスクキュー</strong> — Promise の `.then` / `.catch` / `.finally` コールバック、`queueMicrotask()`
4. <strong>マクロタスクキュー</strong>（タスクキュー） — `setTimeout`、`setInterval`、I/Oコールバック、UIイベント

<EventLoopCycle />

### イベントループの動作順序

ブラウザーのイベントループの1ターンは、次の順序で進みます。

1. タスクを 1 つ取り出して実行する（最初の script、timer callback、入力イベントなど）
2. そのタスクのコールスタックが空になったら、マイクロタスクチェックポイントを実行する。Promise job / `queueMicrotask()` callback をキューが空になるまで処理する
3. 必要に応じてレンダリングを更新する
4. 1 に戻り、次のタスクを取り出す

この順序のため、<strong>マイクロタスクは実行中のタスクに割り込まないが、次のタスクへ進む前にキューが空になるまで処理されます</strong>。次のコードでは、`setTimeout` のコールバック（タスク）より Promise のコールバック（マイクロタスク）が先に実行されます。

```javascript
console.log("1");             // 同期

setTimeout(() => {
  console.log("4");           // マクロタスク
}, 0);

Promise.resolve().then(() => {
  console.log("3");           // マイクロタスク
});

console.log("2");             // 同期

// 出力順: 1, 2, 3, 4
```

### async/awaitの変換

`async/await` はPromiseのシンタックスシュガーとして説明されることが多い構文です。エンジンは実際には関数の実行状態を保存して中断・再開しますが、動作は概念的に次の Promise チェーンと同じです。

```javascript
// async/await で書いたコード
async function example() {
  console.log("A");
  const result = await fetchData();
  console.log("B");
  return result;
}

// エンジンが内部的に行う変換（概念的）
function example() {
  console.log("A");
  return fetchData().then((result) => {
    console.log("B");
    return result;
  });
}
```

`await` 式に到達すると、エンジンは次の処理をします。

1. `await` の右辺の式を評価する。値が Promise でなければ、解決済みの Promise に包む
2. 関数の残りの部分を、その Promise が解決されたときに実行する処理として登録する（Promise が解決されると、再開処理がマイクロタスクキューに入る）
3. 関数の実行を中断し、制御を呼び出し元に返す

そのため、I/O を待っている間もイベントループはほかのタスクを処理できます。

### V8エンジンの最適化

V8（ChromeとNode.jsのJavaScriptエンジン）は v7.2 で `await` を高速化しました。`await` に渡された値がすでにネイティブの Promise の場合、`promiseResolve` でその Promise をそのまま使い、追加のラッパー Promise と `throwaway` Promise を作らなくなりました。これにより、`await` 1回にかかるマイクロタスクのティック数が3から1に減りました。

## Python：asyncioとコルーチン

### Pythonのコルーチン

Pythonの `async/await` はPython 3.5で導入され、<strong>コルーチン</strong>をベースにしています。コルーチンは実行を中断・再開できる関数で、ジェネレーターの仕組みを拡張して作られています。

```python
import asyncio

async def fetch_data():
    print("fetch start")
    await asyncio.sleep(1)  # I/O操作をシミュレート
    print("fetch done")
    return 42
```

`async def` で定義された関数を呼び出しても関数本体は実行されず、コルーチンオブジェクトが返ります。

```python
coro = fetch_data()   # 関数本体はまだ実行されない！
print(type(coro))      # <class 'coroutine'>
```

コルーチンを実行するには、イベントループ（ランタイム）が必要です。

<CoroutineStateMachine />

### asyncioイベントループ

Pythonの `asyncio` モジュールはイベントループの実装を提供します。JavaScriptではランタイムが最初からイベントループを動かしていますが、Pythonでは `asyncio.run()` などで明示的にイベントループを作成・実行する必要があります。

```python
import asyncio

async def main():
    result = await fetch_data()
    print(result)

# イベントループを作成して実行
asyncio.run(main())
```

asyncioのイベントループは、次の3つの仕組みで動いています。

1. <strong>I/O 多重化</strong>: Unix では `SelectorEventLoop` が `epoll` / `kqueue` などの selector backend を使います。Windows の既定は selector API ではなく、IOCP を使う `ProactorEventLoop` です
2. <strong>実行待ちのコールバックのキュー</strong>: イベントループは、すぐに実行できるコールバックをキューに入れ、1つずつ実行します
3. <strong>Task</strong>: `asyncio.Task` はコルーチンを包み、コルーチンを1ステップ進める処理をこのキューに登録します。コルーチンが待っている Future が完了すると、次のステップが再び登録されます

### Pythonのコルーチンの内部実装

Pythonのネイティブコルーチン（`async def`）はジェネレーターとは別の型ですが、CPythonの内部実装ではジェネレーターと同じサスペンド機構（`YIELD_VALUE` オペコード）を共有しています。`await` は `__await__` プロトコルを使い、概念的には次のように動きます。

```python
# 概念的な内部動作
async def example():
    result = await some_coroutine()
    print(result)

# 内部的には（簡略化）:
# 1. some_coroutine() を呼んでコルーチンオブジェクトを取得
# 2. .send(None) で実行を進める
# 3. コルーチンが中断したら、イベントループに制御を返す
# 4. I/O完了後、.send(result) で結果を渡して再開
```

CPython の実装では、コルーチンのフレーム（ローカル変数、実行位置など）はヒープ上に保持されます。そのため、中断・再開のたびにスタックを巻き戻したり復元したりする必要がありません。

### asyncioの制約とGIL

Pythonの `asyncio` には次の制約があります。

- <strong>GIL（Global Interpreter Lock）</strong>: CPythonでは、Pythonバイトコードを実行できるのは一度に1スレッドだけです。asyncioはシングルスレッドで動くので、GILの影響はほとんど受けません
- <strong>CPU-bound処理には向かない</strong>: async/awaitが効果を発揮するのはI/O待ちの多い処理です。CPU-bound処理には `multiprocessing` や `concurrent.futures.ProcessPoolExecutor` を使います
- <strong>ライブラリーの対応が必要</strong>: 同期的なライブラリー（例: `requests`）を async コードから直接呼ぶとイベントループがブロックされるので、非同期版（例: `aiohttp`）を使う必要があります

## Rust：ゼロコストFutureとポーリング

### Rustの非同期モデル

Rustのasync/awaitには、JavaScriptやPythonと違う点が3つあります。

1. <strong>ランタイムが言語に組み込まれていない</strong> — tokio や smol などのサードパーティーのランタイムを選んで使う
2. <strong>Futureはポーリングベース</strong> — コールバックで完了を知らせるのではなく、ランタイムがFutureに完了したかを問い合わせる
3. <strong>ゼロコスト抽象</strong> — 手で状態機械を書いた場合と比べて、async/awaitによる追加のオーバーヘッドがほとんどない

### Future trait

RustのFutureは次のtraitで定義されます。

```rust
pub trait Future {
    type Output;
    
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}

pub enum Poll<T> {
    Ready(T),    // 完了: 結果を返す
    Pending,     // 未完了: 後で再度ポーリングしてほしい
}
```

JavaScriptのPromiseやPythonのコルーチンは、完了した側がコールバックを呼んで知らせる<strong>プッシュベース</strong>です。一方、Rustはランタイムが Future に完了したかを問い合わせる<strong>プルベース（ポーリング）</strong>です。

### async/awaitの状態機械変換

Rustのコンパイラーは `async fn` を状態機械（ステートマシン）に変換します。

```rust
async fn example() -> i32 {
    let a = fetch_a().await;  // 中断点1
    let b = fetch_b().await;  // 中断点2
    a + b
}

// コンパイラーが生成する状態機械（概念的）:
enum ExampleFuture {
    Start,
    WaitingA { future_a: FetchAFuture },
    WaitingB { a: i32, future_b: FetchBFuture },
    Done,
}

impl Future for ExampleFuture {
    type Output = i32;
    
    fn poll(self: Pin<&mut Self>, cx: &mut Context) -> Poll<i32> {
        loop {
            match self.state {
                Start => {
                    self.future_a = fetch_a();
                    self.state = WaitingA;
                }
                WaitingA => {
                    match self.future_a.poll(cx) {
                        Poll::Ready(a) => {
                            self.a = a;
                            self.future_b = fetch_b();
                            self.state = WaitingB;
                        }
                        Poll::Pending => return Poll::Pending,
                    }
                }
                WaitingB => {
                    match self.future_b.poll(cx) {
                        Poll::Ready(b) => {
                            return Poll::Ready(self.a + b);
                        }
                        Poll::Pending => return Poll::Pending,
                    }
                }
                Done => panic!("polled after completion"),
            }
        }
    }
}
```

この変換には次の特徴があります。

- <strong>`await` ごとのヒープ割り当てが必須ではない</strong>: Future は具体的な状態機械の値なので、直接 `await` する場合はスタック上に置けます。一方、Box 化・型消去・ランタイムへの spawn ではヒープ割り当てされます
- <strong>動的ディスパッチが不要</strong>: コンパイル時に具体的な型が確定します
- 各 `await` が1つの状態遷移に対応します

### Waker とランタイムの協調

ポーリングベースのモデルでは、Future をいつ再びポーリングすればよいかをランタイムに伝える仕組みが必要です。これが<strong>Waker</strong>です。

```rust
// Context にはWakerが含まれている
pub struct Context<'a> {
    waker: &'a Waker,
}
```

Future が `Poll::Pending` を返す前に、ランタイムの reactor / driver が OS に I/O の準備完了（readiness）の通知を（epoll/kqueue/IOCP などで）登録し、Future はその driver 側に Waker のクローンを保存します。I/O の準備ができると driver が Waker を呼び、この Future を再びポーリングするようランタイムに知らせます。

```text
1. ランタイムがFuture.poll()を呼ぶ
2. Future は内部で I/O を開始する。ランタイム driver が OS readiness を登録し、Waker を保存
3. Poll::Pending を返す
4. ランタイムは他のFutureをポーリング
5. I/O が ready になる → ランタイム driver が Waker 経由で task を起こす
6. ランタイムが該当Futureを再度poll()
7. Poll::Ready(result) を返す
```

### tokioランタイム

tokioはRustで最も広く使われている非同期ランタイムです。

```rust
#[tokio::main]
async fn main() {
    let result = fetch_data().await;
    println!("{result}");
}
```

tokioは主に次の機能を提供します。

- <strong>マルチスレッドスケジューラー</strong>: work-stealing アルゴリズムでタスクをCPUコア間に分散する
- <strong>I/Oドライバー</strong>: epoll/kqueue/IOCPをラップした非同期I/O
- <strong>タイマー</strong>: 階層型タイマーホイール
- <strong>シングルスレッドモード</strong>: `#[tokio::main(flavor = "current_thread")]` を指定すると、1スレッドのイベントループとして動く

## 言語間の比較

<AsyncComparison />

### プッシュ vs プル

| モデル | 言語 | 仕組み | メリット |
|--------|------|--------|----------|
| プッシュベース | JS, Python | 完了時にコールバック/継続を呼ぶ | 仕組みが単純 |
| プルベース | Rust | ランタイムがFutureをポーリング | ゼロコスト、キャンセルが自然 |

プルベースモデルの利点の1つはキャンセルのしやすさです。Rust では Future をドロップすると、それ以降ポーリングされないので処理が止まります（ただし、ランタイムに spawn したタスクは JoinHandle をドロップしても止まりません）。プッシュベースのモデルでは、JavaScript の `AbortController` のように、キャンセルを明示的に伝える仕組みが必要になることが多いです。

### メモリーモデル

| 言語 | コルーチンの状態保持 | メモリー割り当て |
|------|---------------------|--------------|
| JavaScript | 中断した関数の状態（V8 ヒープ） | GC管理 |
| Python | コルーチンフレーム（ヒープ） | GC管理 |
| Rust | 状態機械（スタック or Box） | 手動制御可能 |
| Go | Goroutine スタック（連続・可変長） | GC管理 + スタック成長 |

### 関数の色問題（Function Coloring）

多くの言語では sync 関数と async 関数がはっきり区別され、「<strong>関数の色問題</strong>」と呼ばれる制約が生じます。

- sync 関数の中では async 関数の結果を `await` で待てない（待つには、スレッドをブロックするか、`asyncio.run()` のようにイベントループを起動する必要がある）
- async 関数から sync 関数は呼べるが、長時間ブロックする処理を呼ぶとイベントループが止まる

```python
# NG: sync から async を直接は呼べない
def sync_function():
    result = await async_function()  # SyntaxError!

# OK: asyncio.run() でブリッジ
def sync_function():
    result = asyncio.run(async_function())
```

Go には async/await がなく、この問題がありません。どの関数も `go` キーワードで新しい goroutine として起動でき、goroutine が I/O で待つ間はランタイムがほかの goroutine を実行します。

## 実践的な注意点

### JavaScriptでの注意

```javascript
// NG: awaitを忘れるとPromiseオブジェクトが返る
async function bad() {
  const data = fetch("/api");  // await がない！
  console.log(data);            // Promise オブジェクトが出力される
}

// NG: 直列実行になってしまう
async function sequential() {
  const a = await fetchA();  // 1秒待ち
  const b = await fetchB();  // さらに1秒待ち → 合計2秒
}

// OK: Promise.all で並行実行
async function parallel() {
  const [a, b] = await Promise.all([fetchA(), fetchB()]);  // 合計1秒
}
```

### Pythonでの注意

```python
# NG: ブロッキングI/Oをasyncコード内で使う
async def bad():
    import requests
    response = requests.get("https://example.com")  # イベントループをブロック！

# OK: 非同期ライブラリーを使う
async def good():
    import aiohttp
    async with aiohttp.ClientSession() as session:
        response = await session.get("https://example.com")

# 独立したタスクの並行実行
async def gather_example():
    results = await asyncio.gather(
        fetch_a(),
        fetch_b(),
        fetch_c(),
    )
```

### Rustでの注意

```rust
// NG: async fn内でブロッキング操作
async fn bad() {
    std::thread::sleep(Duration::from_secs(1)); // ランタイムのスレッドをブロック！
}

// OK: tokioの非同期版を使う
async fn good() {
    tokio::time::sleep(Duration::from_secs(1)).await;
}

// OK: CPUバウンド処理はspawn_blockingで別スレッドに逃がす
async fn cpu_work() {
    let result = tokio::task::spawn_blocking(|| {
        heavy_computation()
    }).await.unwrap();
}
```

## まとめ

async/awaitの構文は言語間で似ていますが、裏側の実装は大きく異なります。

- <strong>JavaScript</strong>: シングルスレッドのイベントループの上で、Promise を使って中断・再開する。マイクロタスクとマクロタスクの優先順位が実行順を決める
- <strong>Python</strong>: asyncioのイベントループがコルーチン（ジェネレーターの拡張）をスケジューリングする。GILの制約の下で、I/O待ちを並行に進める
- <strong>Rust</strong>: async fn を Future の状態機械に変換する。ランタイムがポーリングで実行を進め、`await` ごとのヒープ割り当てを必須にしない

3つに共通するのは、<strong>I/O を待つ間スレッドを遊ばせない</strong>という設計です。async/awaitは、こうした非同期処理を同期コードに近い形で書けるようにする構文です。
